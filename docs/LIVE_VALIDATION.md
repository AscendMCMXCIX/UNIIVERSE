## Automated live check

**It runs by itself (3 Nov 2026):** GitHub's Production check (`.github/workflows/production-check.yml`) runs it after each production deployment and every day, from GitHub's runner, with no setup by anyone. Since 7 Nov 2026 it signs in as the verification account (below) and checks the member pages too. A lost sign-in fails the check and opens its issue: the account withdrawn, a conflict, no answer from its job, no `CRON_SECRET`, a key the app cannot use, or the repository's `VERIFY_ACCOUNT_SECRET` missing or padded while the app uses it ("When the account is lost, the check fails", below). Only the owner's two off switches, `SIGNED_IN_CHECKS` set to `false` or `verify` deactivated in Admin, leave the member pages pending instead (a key the app cannot use still fails the run); the run then checks the public pages and the signed-out security only. The numbered items below that need a signed-in member, and the pages the check does not open, stay for a person (`docs/MONITORING.md`).

`scripts/live-check.mjs` checks the deployed site from a browser. It runs the read-only checks that people otherwise do by hand, at desktop (1440 px), tablet (768 px) and phone (390 px) widths, and saves a screenshot of every page for review.

```
node scripts/live-check.mjs [base url] [output folder]
```

- **Base url:** defaults to https://team-uniiverse.vercel.app.
- **Output folder:** defaults to `live-check-<time>`. It holds the screenshots, `report.json` and `summary.md`. The run exits with 1 when any check fails.
- **Sign-in:** `UNIIVERSE_VERIFY_USER` and `UNIIVERSE_VERIFY_PASSWORD`, for a non-admin team member who is not in the lineup. They are read from the environment and never printed. In a cloud session they go in the environment's settings, and the site must be under its allowed domains.
- **The verification account** (no owner step; since 7 Nov 2026). The job `verify-account` keeps a member account called `verify` with **no player profile**. The Production check calls it before signing in, and it can also be run by hand from Data jobs (production only):
  - **Invisible to members:** it is in no list a member sees. Players, the lineup, leaderboards and statistics all read player profiles.
  - **Nothing collected:** it has no Riot account, so no Riot request is ever made for it, and it cannot give itself a player profile: only the Owner completes a missing profile under My profile (`completeProfileAction`); every other profile is created by an administrator with the account. Its visits act as any member's do: opening a teammate's profile refreshes that teammate's Riot data when it is due (last synced 15 or more minutes earlier; one bounded 40 s sync), and an open game can check its players' ranks (below).
  - **Not counted as a member's use:** its page loads are left out of the field measurements (Admin → System Health → Page speed in members' browsers): `/api/vitals` drops the beacons of `verify` with no profile (`src/server/auth/verification-account.ts`). Until that change went live (7 Nov 2026, about 18:27 UTC) they were counted: about 30–40 loads per signed-in run, from the first one at 11:17 UTC that day. Those stay in the 28-day figures until 4 Dec.
  - **Access:** exactly the default member access: no access level of its own, no access group, no custom permissions and no administrator rights. It is the access a new member gets: Team, Players, a teammate's statistics, Matches. Its own Settings cannot change its username, display name or password (`src/server/auth/verification-account.ts`). Since 19 Nov 2026 Admin cannot change it either: an access level, groups, permissions, administrator access, its role, a password reset or an erasure are refused on the server (`guardVerificationAccount` in `src/server/auth/account-admin.ts`, `guardErasure`), and Users & Permissions shows it locked under **Kept automatically**, with Deactivate and Delete only.
  - **Sign-in:** through the normal sign-in form, with the normal password check and throttling.
  - **Its password is never typed, stored or shown.** It is worked out (an HMAC with a fixed label; `src/server/jobs/verify-account.ts`) from a key the app and the Production check both hold: `VERIFY_ACCOUNT_SECRET`, a secret of its own, once the owner has set it, and `CRON_SECRET` until then. The job's answer names the key it used, by name only, and the Production check works the password out from the same one; the workflow masks it the moment it computes it. Whoever holds the key can therefore open one member session with the default member access. Until `VERIFY_ACCOUNT_SECRET` is set, that is whoever holds `CRON_SECRET`, which on its own authorises only the jobs endpoint and also lives in Supabase Vault and in every pg_cron call; once it is set, `CRON_SECRET` opens no member session, and each of the two can be replaced without the other. After a change of the key, the next Production check updates the password by itself and ends the account's sessions.
  - **Setting `VERIFY_ACCOUNT_SECRET`** (the owner, once; until then nothing changes): make one random value with `openssl rand -base64 48` (at least 32 characters, no space or line break at either end, not `CRON_SECRET`'s value) and keep it nowhere else. Add it first as the repository secret `VERIFY_ACCOUNT_SECRET` (GitHub → Settings → Secrets and variables → Actions), then in Vercel (Project → Settings → Environment Variables, the Production environment only, never Preview), and redeploy. The Production check after that deploy logs `verification account: password-updated` and `verification account key: VERIFY_ACCOUNT_SECRET` and signs in; later runs log `unchanged`. If the repository's copy is missing or has a space or line break at an end, the check fails and says so; if it differs, the sign-in fails. A value the app cannot use fails the check with the app's one sentence of rules, which says which rules there are, not which one failed (the job's answer is printed in public logs); meanwhile the password `CRON_SECRET` gave is withdrawn and the account's sessions end, so `CRON_SECRET` does not keep opening it, and once the value is fixed the next run sets the new password. The check calls the job on every run that has `CRON_SECRET`, whoever signs in, so the account follows a change of its key with the signed-in checks switched off or explicit `UNIIVERSE_VERIFY_*` secrets set too; such a run fails only on a key the app cannot use, and says any other answer as a warning. Deleting `VERIFY_ACCOUNT_SECRET` from Vercel and redeploying puts the account back on `CRON_SECRET`.
  - **What the job does:** it creates the account, changes nothing when run again, or updates the password after a change of its key. If its own account (the derived password or, just after `VERIFY_ACCOUNT_SECRET` was set, the one `CRON_SECRET` gave) was given more access, an access level, a group, a profile or another name, it withdraws the password and ends its sessions (`withdrawn`), so no key opens it; until the change is undone, each run ends any session it still has (a sign-in that raced the withdrawal), and then the next run sets the password again. An account of that name that is not the plain member it keeps, and whose password is not the derived one, it never touches: an active one answers `conflict`, a deactivated one `deactivated`. A plain account with another password gets the derived one back on the next run (`password-updated`), so a password set some other way (a script, the database) does not stick; Admin refuses a reset since 19 Nov 2026; deactivated, it stays deactivated, but its password still follows a change of the key, so reactivating it never reopens it to the key before. It records its changes in Admin → Audit Logs.
  - **When the account is lost, the check fails:** `withdrawn`, `conflict` or no answer from the job fails the Production check and opens its issue, as do a missing `CRON_SECRET`, a key the app cannot use (a `VERIFY_ACCOUNT_SECRET` under 32 characters, with a space or line break at an end, or `CRON_SECRET`'s value; a `CRON_SECRET` too short to derive from: the check shows the app's fixed sentence, the only error text of the job's it prints), and the app using `VERIFY_ACCOUNT_SECRET` while the repository's copy is missing or padded. Two cases cannot be caught: between a change to the account made outside Admin (a script, the database; Admin refuses them since 19 Nov 2026) and the job's next run (each deploy, and 05:37 UTC daily) the derived password still opens it; and an account changed and its key replaced before any run of the job answers `conflict` (a failure), while the old derived password still opens it until the owner deactivates or deletes it. Setting `VERIFY_ACCOUNT_SECRET` for the first time is the exception: the job still recognises the password `CRON_SECRET` gave and withdraws it. Read the first Production check after each change of the key.
  - **To turn the signed-in checks off:** deactivate `verify` in Admin (the account then cannot sign in at all), or set the repository variable `SIGNED_IN_CHECKS` to `false` (this only stops the sign-in: the check still keeps the account, so its password follows a change of the key, and the account stays usable with that key). Either way the member pages are reported as pending, not as a failure. Deleting the account does not turn them off: the next run creates it again. Explicit `UNIIVERSE_VERIFY_USER` / `UNIIVERSE_VERIFY_PASSWORD` secrets, if set, take precedence.

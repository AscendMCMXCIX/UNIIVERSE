# Monitoring and alerts

What tells the owner that UNIIVERSE is unwell, what does not yet, and how to close the gaps for free. Nothing here costs money on the current free plans.

**Status (4 Nov 2026):** no paid monitoring and no third-party monitor are set up. The signals below come from GitHub, Vercel, Supabase and the app itself. Scheduled Data jobs runs fail when production is unwell (audit decision 10) or when a day's database egress goes over its budget. The **Production check** checks the live site in a browser after each production deployment and every day, and the **Database backup** watches its own size; both report through one GitHub issue each, opened while failing and closed on recovery.

## What is watched today

| Signal | Where | Who hears about it |
|---|---|---|
| The app or its database is down | `GET /api/health`: `503` with `db.ok: false` when the database does not answer. Scheduled Data jobs runs read it and fail | GitHub's failed-workflow email (below) |
| A scheduled Data jobs run cannot reach the app | `.github/workflows/data-jobs.yml`, hourly (GitHub delivers about 4 a day). The run fails when the tick endpoint answers with an error | GitHub emails the account that last changed the workflow's schedule, if that account has Actions notifications turned on |
| A data job fails, or is killed before it finishes (Riot sync, champion sync, audits) | `/api/health` → `failingJobs`: a job whose last run failed or never finished, from the first such run until a run succeeds (also while it is being run again). A run still "running" after 15 minutes counts as killed; the next run or the daily `integrity` job records it as a failed run. Admin → System Health once it happened three times in a row. Scheduled Data jobs runs fail while it is listed | GitHub's failed-workflow email (below) |
| The static refresh fails or goes stale (Data Dragon's item, summoner and rune files for the current game version fail validation, cannot be downloaded for a day, or version-check stops succeeding) | `/api/health` → `failingJobs` lists `static-data`, and `staticData` says why: `{ state: "failed" \| "stale" \| "ok", patch, stored, reason: "validation" \| "download" \| "no-success" \| null, problems: { empty, missingIds, unparsedHaste } \| null }` (patch names and counts only; `src/server/ops/static-health.ts`). Failed at once when the current version's files fail validation (the last good copy stays in use, `assets.ts`); stale when they could not be downloaded for 24 hours (about 24 hourly attempts), or no `version-check` or `static-sync` run has succeeded for 72 hours. Chosen so a normal week never trips it: Riot ships a patch about every two weeks, version-check runs every hour and a run with nothing new succeeds, and Riot's own files pass validation (0 problems at five versions from 15.10 to 16.23); an afternoon's Data Dragon outage is not an alert, a day without the new patch's items is. Not listed while version-check is set to 0 in Admin (a notice says so). Scheduled Data jobs runs fail while it is listed | GitHub's failed-workflow email (below) |
| Linked accounts stop syncing | `/api/health` → `data.accounts`, when a linked account was last read from Riot in full (from the accounts themselves: the `account-sync` job records a success when it had nothing to do, no key, or every account failed). Scheduled runs fail when it is older than 12 hours (repository variable `SYNC_STALE_HOURS`) | GitHub's failed-workflow email (below) |
| Riot rejects the API key (a development key expired, a key revoked), or refuses one request the account sync needs (one API, or a routing host that does not serve it) | `/api/health` → `riot.credential` is `rejected` and `failingJobs` lists `riot-key`, from Riot's 401/403 until Riot accepts a request under the key again; a failure with no answer (a 5xx, a rate limit, a network error) does not clear it. The account sync alone would not show it: every linked account then waits, backing off for up to about five hours, and its runs find nothing due and succeed. Admin → Data & Integrations names the key in use and what to do. A scheduled Data jobs run that finds it listed first asks again, once (`riot-check`, which records the answer). While a refusal is recorded, `riot-check` asks platform status and then each request an account sync makes, on the host the sync uses, for one linked account per server in use (up to four servers; a match's details only when that account has a Ranked Solo/Duo game). It starts no request more than 30 s after it began and a request already sent ends within 7 s, so it answers inside the run's 45 s wait for it; a check that runs out of time records nothing and answers `unavailable`, so the refusal stands. It answers `accepted` only when Riot accepts them all, as after a short Riot-side 401/403 incident: the run then drops `riot-key` with a warning and does not fail on it. Otherwise (a request still refused, which `riot-check` and Admin name by API and host; unavailable, out of time included; an unreadable answer or none) it fails and names the re-check's result | GitHub's failed-workflow email (below) |
| Some linked accounts cannot be synced | The `account-sync` run is *degraded* whenever an account it tried could not be synced. Its error counts them (it never names an account; "none of the N" when every one failed, which is how a rejected key or a Riot outage looks); Admin → Data & Integrations repeats it as a warning, and each player's Riot Accounts tab says why | Only someone who looks |
| The five-minute rank schedule goes silent (its calls refused after a `CRON_SECRET` change, pg_cron stopped, the job removed or made inactive by hand, a restore into a new project) | `/api/health` → `failingJobs` lists `rank-schedule` while the schedule is installed (the `rank-schedule` job's last success is later than `rank-schedule-off`'s) and it has not called the app for 20 minutes: each authorised direct call of `/api/jobs/rank-watch`, the call the schedule sends, is recorded as it arrives (`src/server/ops/rank-schedule-calls.ts`). The rank watch's own successes are not used, because ticks (the ten-minute pg_cron tick, GitHub's runs, visits) run it too and would hide a silent schedule. A refused call records nothing in the app, so this silence is the only sign. Data jobs `rank-schedule-status` then says why (calls by HTTP status, whether Vault matches the server's secret); after a `CRON_SECRET` change, run Data jobs `rank-schedule` again | GitHub's failed-workflow email (below) |
| The five-minute rank schedule is turned off after it was on (Data jobs or Admin's `rank-schedule-off`; on 18 Nov 2026 at 09:04 UTC it was, from Admin's Run now list, and nothing said so for 22 hours), or a job the tick runs is set to 0 in Admin (it then never runs by itself: `version-check` at 0 would stop patch detection) | `/api/health` → `notices` (since 19 Nov 2026; `src/server/ops/health-notices.ts`): "LP five-minute schedule off since <day>" while `rank-schedule-off`'s last success is later than `rank-schedule`'s (and `rank-schedule` has succeeded once), and "Off by choice (interval 0 in Admin): <keys>" for the tick's jobs at 0 in the schedule overrides (one `app_settings` row, the only extra read; still no pg_cron or Vault read here). A notice is not a failure: turning either off now takes the Owner's typed phrase in Admin (Data & Integrations → Advanced), so it is deliberate. The answer is public: the day and the job keys only, never who did it, an audit entry or a link; Admin → Audit Logs → Data & jobs names who ran it | A warning in every Production check (each notice, by its words) until it is turned on again; no email (a silent installed schedule still fails, row below) |
| The database's ten-minute tick goes silent on its own (production's `uniiverse-tick`: its calls refused, the job removed or made inactive by hand, its command broken; pg_cron stopping shows as `rank-schedule` too) | `/api/health` → `failingJobs` lists `tick-schedule` once the tick has called the app and then not for four of its intervals: 40 minutes for the ten-minute tick, never less than 40 minutes or more than four hours, from the time between its last two calls, so a tick that runs less often than every four hours, or pauses (by day only), is listed in each of its gaps (docs/DEPLOYMENT.md, 4 c). Each authorised call of `/api/jobs/tick` that pg_net sends is recorded as it arrives (`src/server/ops/tick-schedule-calls.ts`), known by the User-Agent pg_net gives every request (`pg_net/<version>`). GitHub's runs (curl), Vercel's cron (`vercel-cron/1.0`) and visits never carry it, so they cannot hide a silent tick; a missing tick run alone would prove nothing, since they run ticks too. A refused call records nothing, so the silence is the sign. Data jobs `rank-schedule-status` shows when the app last recorded each schedule's call (`callsRecordedByApp`) beside the pg_cron jobs and their calls; a tick whose command sends a User-Agent of its own is never recorded, and so never listed. To remove the tick on purpose, or to leave it out after a restore into a new project (the restore brings its record back, docs/BACKUPS.md), also delete its record (docs/DEPLOYMENT.md, 4 c); a pause longer than 40 minutes lists it until its next call | GitHub's failed-workflow email (below) |
| The rank watch reads no account in a run (a Riot outage, timeouts, the network, or no room in the rate limits) | The `rank-watch` run is *degraded* when every account it tried failed, and says how many it tried, counts only; also when a full rate limit stopped it before its first reading (account sync and the rank checks share the key), saying how many accounts were due and that the next run, five minutes later, reads again. Admin → Data & Integrations repeats either message as a warning. The run still answers ok, so the schedule's call is not refused, and it is not listed in `failingJobs`, so neither a Riot outage nor a busy key fails the scheduled run | Only someone who looks |
| The rank checks after collection check nobody in a run (a Riot outage, timeouts, the network, ids the key cannot read) | The `rank-checks` run is *degraded* when every player it asked failed, and says how many it asked, counts only; its log counts the failures by what they met (Riot's status, no readable answer, an answer not stored), and Admin → Data & Integrations repeats the message as a warning. It is not listed in `failingJobs`, so a Riot outage does not fail the scheduled run | Only someone who looks |

After every production deployment the Production check runs by itself (`CLAUDE.md` §5). A manual Data jobs run is only needed for `auth-audit` after a migration, or `perf-probe` outside the Production check's Monday run.

## Page speed in members' browsers (field data)

Lighthouse and the browser tests measure one emulated device in a lab (`docs/PERFORMANCE.md`). The field figures come from members' own phones, tablets and computers. The two are reported apart and never mixed.

- **What is measured.** On every signed-in page (Player Mode and Admin Mode), the browser reports Google's Core Web Vitals through Next.js's own `useReportWebVitals`, with no extra library: Largest Contentful Paint, Interaction to Next Paint and Cumulative Layout Shift, plus First Contentful Paint and Time to First Byte. Each browser reports what it supports; a browser without a measure sends none.
- **What is sent** (`src/components/web-vitals-reporter.tsx`): once, when the page is hidden (closed, left or put in the background), one small beacon carrying:
  - each measure's bucket number, not its value (the buckets are in `src/domain/web-vitals.ts`);
  - the page group: the first part of the address, such as `players`, never an id;
  - the device class: phone, tablet or desktop, from the window width.

  Nothing identifies the member, their account or what they opened. Moving between pages inside the app is not a new load, so INP keeps counting for the page the app was opened on.
- **What is stored** (`web_vitals_daily`): a count per UTC day, measure, bucket, page group and device class, kept 35 days (migration `0054_web_vitals`, Row Level Security on, closed to Supabase's Data API).
- **Who may send:** the endpoint counts a beacon only for a signed-in member, from this site, well formed and at most 1 KB, and at most 120 a minute per server instance. Anything else is dropped without an error. A forged beacon can only add to counts. It cannot read anything or write anywhere else.
- **Where to read it:** Admin → System Health. For each measure it shows the value 75% of loads stayed within, and the good, needs-work and poor shares. Those three use Google's thresholds, which are bucket bounds, so the shares are exact. It also breaks the figures down by device class and by page group.
- **Cost.** One write per page load, which is not database egress, and no new service. The panel's read is one grouped query of a few hundred rows at most. The browser code is the reporter and Next.js's bundled web-vitals; its size is in `docs/PERFORMANCE.md`.
- **Off switch:** `UNIIVERSE_FIELD_METRICS=off` stops both the measuring and the storing.

## How an alert reaches the owner

A scheduled Data jobs run (hourly; GitHub delivers about 4 a day) starts the tick, then reads `/api/health`. It fails, naming the problem in the run's log, when:
- the app or its database does not answer, or the answer cannot be read;
- `failingJobs` is not empty: a job whose last run failed or was killed before it finished, until a run succeeds, or `riot-key` while Riot refuses a request under the configured key, unless Riot accepts the key and the account sync's requests when the run asks again (one `riot-check` call: then a warning, not a failure), or `rank-schedule` while the installed five-minute rank schedule has not called the app for 20 minutes, or `tick-schedule` once the database's ten-minute tick has called and then been silent for four of its intervals (40 minutes), or `static-data` while the static refresh failed validation or has gone stale (above);
- the account sync has not succeeded for 12 hours;
- yesterday's database egress, as counted by the app, was over the daily budget (120 MB unless `EGRESS_DAILY_BUDGET_MB` says otherwise). The log names the five largest query shapes. A deployment that does not have the check yet is a warning, not a failure.

A failed scheduled run is reported by GitHub's usual email. It goes to the scheduled runs' actor (the account that last changed the workflow's schedule, AscendMCMXCIX), and only if that account has GitHub → Settings → Notifications → System → Actions with **Email** selected; "Only notify for failed workflows" only cuts the noise of successful runs. No API can confirm the setting, so the owner confirms it (STATUS.md, "Needs the owner"). The check costs no extra Actions minutes: it is part of the same one-minute run, with no new workflow or schedule.

Each failing run sends one email until the problem is fixed, so a fault that lasts a day sends about four.

The Production check and the Database backup (in the private backup repository) report the same way: one issue per check (labels `production-check`, `database-backup` and `backup-age`, `scripts/report-issue.sh`), opened by the first failing run with what failed and the run's link, commented on by later failing runs, and closed by the next passing run. A new issue notifies the owner as any issue on their repository does; nothing needs tidying after a recovery.

## Still not covered

- **Nothing checks from outside GitHub.** If GitHub Actions is paused (it disables scheduled workflows after 60 days without a commit), the alerts stop too. A free outside uptime monitor on `/api/health` would cover this; the owner creates its account, and no credentials go through the repository.
- **Between scheduled runs,** a fault is noticed only at the next run (hours at worst).
- **Signed-in pages from outside:** the Production check signs in as the verification account `verify` (Data jobs `verify-account`, its password worked out from `VERIFY_ACCOUNT_SECRET`, or from `CRON_SECRET` until the owner sets it; docs/LIVE_VALIDATION.md) and opens the member pages at three widths. A lost sign-in (the account withdrawn, a conflict, no answer, no `CRON_SECRET`) fails the check and opens its issue; only the owner's off switches (`SIGNED_IN_CHECKS=false`, or the account deactivated) leave the member pages pending. Explicit `UNIIVERSE_VERIFY_USER` / `UNIIVERSE_VERIFY_PASSWORD` secrets would take its place. It cannot open a member's own profile, Overview or first-time setup (CI covers them on demo data).

Until an outside monitor exists: open Admin → System Health now and then, or run Data jobs `smoke` after anything unusual.

## What `/api/health` returns

- **Fields:** `ok`, `deployment.commit` and `region`, `auth.mode`, `db` (`ok`, `ms`), the current `patch`, when champions and accounts last synced, each job's `status` and `lastSuccessAt`, `failingJobs` (failing jobs by key, plus `riot-key`, `rank-schedule`, `tick-schedule` and `static-data` as above), `notices` (what is off by choice, above: `{ kind: "schedule-off", job: "rank-schedule", since: "2026-11-18", message }` and `{ kind: "disabled", jobs: [...], message }`; never a failure, never who), `digests` (since 20 Nov 2026: Matchup Intel's per-version diff of Data Dragon, `src/server/matchup-intel/digests.ts`: `{ patch, recorded: { champion, item, rune }, previous, changed: { champion, item, rune } | null }`, the newest patch with digests, how many of each it recorded, the patch before it with digests and how many of each changed since (of those both patches recorded: a new key is not a change); `null` before any patch is recorded, `changed` null without an earlier patch to compare with; counts and patch names only, never a champion, item or rune), `staticData` (since Release 11: the static refresh's state, above), and `riot.credential`: the state of the configured Riot key as the jobs last recorded it (`accepted`, `rejected`, `unavailable`, `unknown` or `not-configured`), the word only, never the key or its fingerprint.
- **HTTP status:** `503` when the database does not answer, otherwise `200`.
- **Privacy:** no secrets and no personal data; database errors have connection strings redacted. Anyone can read it, like the sign-in page.

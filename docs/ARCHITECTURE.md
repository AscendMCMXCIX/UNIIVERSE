# Architecture

UNIIVERSE is a single Next.js 16 application (App Router, TypeScript, Tailwind v4) with a PostgreSQL database. There are no microservices: background work runs as *jobs* inside the same codebase, triggered by any scheduler that can call a URL.

## Layers

| Layer | Location | Notes |
| --- | --- | --- |
| Domain | `src/domain` | Pure TypeScript, no I/O. Roles, tournament sequence, draft state machine, player eligibility, legal role assignments, statistics shrinkage, champion characteristics, composition model, recommendation engine, game plan. Everything here is unit tested. |
| Server | `src/server` | Database (Drizzle ORM), repositories, Riot static/API providers, pro-data providers, ingestion, aggregation, stats loader, jobs, scheduler, auth, server actions. |
| UI | `src/components`, `src/app` | Server components for pages, client components for interactive parts (draft room, champion picker, editors). |

Dependency direction is strictly UI → server → domain. The domain never imports from the server.

## Database

- Production: PostgreSQL (Supabase recommended) through `postgres-js`, `prepare: false` for pooler compatibility.
- Local/demo/tests: [PGlite](https://pglite.dev) (embedded Postgres) persisted in `./.data`, or in memory for tests.
- Migrations are generated by `drizzle-kit` into `drizzle/` and **embedded** into the app (`src/server/db/migrations.generated.ts`) so every instance migrates itself on first connection, serialised by a Postgres advisory lock. No separate migration step on deploy.

Main tables (see `src/server/db/schema`):

- `teams`, `players`, `player_champion_pools`, `lineups`, `lineup_slots`
- `champions`, `patches`, `champion_change_points`
- `drafts`, `draft_actions` (with the recommendation snapshot at the time), `draft_role_swaps`
- `tracked_summoners`, `match_fetch_queue`, `ranked_matches`, `ranked_participants`, `ranked_bans`
- `pro_games`, `pro_game_picks`, `pro_game_bans`
- `stat_periods`, `champion_role_stats`, `champion_ban_stats`, `champion_matchups`, `champion_synergies` – keyed by `(patch, source)`; history is never overwritten
- `data_refresh_status`, `job_runs`, `app_settings`

## Request flow in the Draft Room

1. The page loads the draft, its actions and the lineup snapshot (pools as they were when the draft started).
2. `recommendForDraft` builds the champion map (synced roster + curated profiles), loads the cached statistics provider for the current patch, and calls the domain `recommend()`.
3. Each ban/pick is a server action: validate against the sequence, persist the action (plus a snapshot of what was recommended), recompute recommendations, and when the draft completes, generate and store the game plan.

A recommendation takes about 50–100 ms; statistics are precomputed by the aggregation job and cached in memory per patch/stats version.

## Automation

`src/server/jobs/scheduler.ts` implements a *tick*: it runs every job whose interval has elapsed, in dependency order (static → ranked → pro → aggregate → integrity), within a time budget. Any scheduler can call `GET /api/jobs/tick` with `Authorization: Bearer $CRON_SECRET`. Individual jobs are available at `/api/jobs/<name>` and from the CLI (`pnpm job <name>`). Intervals live in `app_settings` and are editable in Settings.

Every job is idempotent and resumable: match ids are primary keys, aggregation marks matches in the same transaction that increments the counters, and a failing provider leaves the last-known-good data in place while the job is recorded as *degraded*.

## Authentication

Private by default. A team password (`UNIIVERSE_ACCESS_PASSWORD`) grants editing; optional viewer/editor passwords give read-only or secondary editing access. Sessions are signed JWT cookies (`jose`). The `src/proxy.ts` route proxy enforces this for pages; job endpoints use `CRON_SECRET`. Locally with no password configured the app is open (owner). In production with missing configuration the app shows a setup page instead of running insecurely.

## Future-proofing

- No hard-coded patch, champion count or season: versions come from Data Dragon, champions from the synced roster, statistics periods from the data itself.
- New champions appear automatically with a *derived*, low-confidence characteristic profile until curated in `src/domain/champion-model/curated-data.ts`.
- Provider parsing is isolated per adapter (`src/server/riot/api/schemas.ts`, `src/server/pro/*`) and validated with zod; a schema change marks the provider degraded without touching stored data.

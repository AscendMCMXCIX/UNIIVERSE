# Architecture

UNIIVERSE is a single Next.js 16 application (App Router, TypeScript, Tailwind v4) with a PostgreSQL database. There are no microservices: background work runs as *jobs* inside the same codebase, triggered by any scheduler that can call a URL.

## Layers

| Layer | Location | Notes |
| --- | --- | --- |
| Domain | `src/domain` | Pure TypeScript, no I/O. Roles, tournament sequence, draft state machine, player eligibility, legal role assignments, statistics shrinkage, champion characteristics, composition model, recommendation engine, game plan. Everything here is unit tested. |
| Server | `src/server` | Database (Drizzle ORM), repositories, Riot static/API providers, pro-data providers, ingestion, aggregation, stats loader, jobs, scheduler, auth, server actions. |
| UI | `src/components`, `src/app` | Server components for pages, client components for interactive parts (draft room, champion picker, editors). |

Dependency direction is strictly UI → server → domain. The domain never imports from the server.

## Database

- Production: PostgreSQL (Supabase recommended) through `postgres-js`, `prepare: false` for pooler compatibility.
- Local/demo/tests: [PGlite](https://pglite.dev) (embedded Postgres) persisted in `./.data`, or in memory for tests.
- Migrations are generated by `drizzle-kit` into `drizzle/` and **embedded** into the app (`src/server/db/migrations.generated.ts`) so every instance migrates itself on first connection, serialised by a Postgres advisory lock. No separate migration step on deploy.

Main tables (see `src/server/db/schema`):

- `teams`, `players`, `player_champion_pools`, `lineups`, `lineup_slots`
- `champions`, `patches`, `champion_change_points`
- `drafts`, `draft_actions` (with the recommendation snapshot at the time), `draft_role_swaps`
- `tracked_summoners`, `match_fetch_queue`, `ranked_matches`, `ranked_participants`, `ranked_bans`
- `pro_games`, `pro_game_picks`, `pro_game_bans`
- `stat_periods`, `champion_role_stats`, `champion_ban_stats`, `champion_matchups`, `champion_synergies` – keyed by `(patch, source)`; history is never overwritten
- `data_refresh_status`, `job_runs`, `app_settings`

## Request flow in the Draft Room

1. The page loads the draft, its actions and the lineup snapshot (pools as they were when the draft started).
2. `recommendForDraft` builds the champion map (synced roster + curated profiles), loads the cached statistics provider for the current patch, and calls the domain `recommend()`.
3. Each ban/pick is a server action: validate against the sequence, persist the action (plus a snapshot of what was recommended), recompute recommendations, and when the draft completes, generate and store the game plan.

A recommendation takes about 50–100 ms; statistics are precomputed by the aggregation job and cached in memory per patch/stats version.

## Automation

`src/server/jobs/scheduler.ts` implements a *tick*: it runs every job whose interval has elapsed, in dependency order (static → ranked → pro → aggregate → integrity), within a time budget. Any scheduler can call `GET /api/jobs/tick` with `Authorization: Bearer $CRON_SECRET`. Individual jobs are available at `/api/jobs/<name>` and from the CLI (`pnpm job <name>`). Intervals live in `app_settings` and are editable in Settings.

Every job is idempotent and resumable: match ids are primary keys, aggregation marks matches in the same transaction that increments the counters, and a failing provider leaves the last-known-good data in place while the job is recorded as *degraded*.

## Team platform additions (session 2)

- **Accounts**: `users`, `invites` (scrypt password hashes, JWT session cookie, roles owner/coach/player). Local development runs an implicit owner session; production requires `UNIIVERSE_AUTH_SECRET` and creates the owner through a one-time setup key.
- **Riot accounts**: `riot_accounts` (PUUID unique, Riot ID unique per platform), `account_champion_history`, `account_matches` (ledger so a match is folded exactly once), `account_mastery`; `src/server/accounts/sync.ts` is incremental and the `account-sync` job runs it in batches.
- **Series**: `series` (mode, event, opponent label, best-of, running score, status); `drafts.series_id`/`game_number` and `matches.series_id`/`game_number` tie games to it. Pure rules in `src/domain/series.ts`; the score is recomputed from recorded results (`src/server/series/repository.ts`).
- **Enemy names**: `drafts.enemy_players` and `matches.enemy_players` (optional names by role). The former scouting tables `opponent_teams` / `opponent_players` remain in the database but are no longer written or shown.
- **Draft formats and modes**: formats are data (`src/domain/draft/formats.ts`), custom ones live in `app_settings.draft_formats` and are embedded into each draft so history never changes.
- **Live drafts**: `drafts.version` (optimistic concurrency), `drafts.controller_user_id`, `draft_presence`; `GET /api/drafts/[id]/stream` is a server-sent-events feed that polls the version and presence.
- **Matches**: `matches` archive rows created on completion; the playbook (`src/domain/playbook`) is stored as drafted. Nothing reads the archive back into the engine.
- **Branding**: `app_settings.branding` (validated in `src/domain/branding.ts`), applied as CSS variables on the app shell. The UNIIVERSE mark, wordmark and backdrop ship in `public/brand/` (favicon and Apple icon are `src/app/icon.png` and `src/app/apple-icon.png`); the mark is shown wherever no custom logo is set, the wordmark and backdrop only on the sign-in, first-run and invite pages (`src/components/auth/brand-frame.tsx`). The default accent is the brand cyan; a team can still override name, colour and logo in Settings.

## Authentication

Private by default. Members have their own accounts (username, unique case-insensitively, plus an optional scrypt-hashed password; email is a nullable legacy column) with the roles **owner** (everything), **coach/analyst** (draft control, matches, players) and **player** (view everything live, edit only their own profile). Creating an account (`src/server/auth/signup.ts`) inserts the user, the player profile and the primary and optional additional Riot accounts in one transaction; Riot IDs are resolved to PUUIDs later by `account-sync`, so Riot being down never blocks sign-up. The owner creates single-use link invites; an invite may point at a roster placeholder that the new account takes over. Accounts that predate automatic profiles complete theirs once under `/me` (`completeLegacyProfile`, race-safe). Sessions are rows in `sessions` (`src/server/auth/sessions.ts`): the browser holds an opaque HTTP-only cookie, the database its SHA-256 hash; 30 days by default, 365 with "Remember this device" (`src/server/auth/config.ts`, overridable by `UNIIVERSE_SESSION_DAYS` / `UNIIVERSE_SESSION_REMEMBER_DAYS`); logout deletes the row, a password change or reset deletes every row of that user. Cookies issued before the sessions table existed are signed JWTs and stay valid until they expire. `src/proxy.ts` sends anonymous visitors to `/login`; job endpoints use `CRON_SECRET`. Locally with no configuration the app runs as an implicit local owner (no login). In production the first visit shows a setup page that requires the one-time `UNIIVERSE_ACCESS_PASSWORD` setup key to create the owner; with `DATABASE_URL` or `UNIIVERSE_AUTH_SECRET` missing it refuses to run insecurely and explains what to set.

## Future-proofing

- No hard-coded patch, champion count or season: versions come from Data Dragon, champions from the synced roster, statistics periods from the data itself.
- New champions appear automatically with a *derived*, low-confidence characteristic profile until curated in `src/domain/champion-model/curated-data.ts`.
- Provider parsing is isolated per adapter (`src/server/riot/api/schemas.ts`, `src/server/pro/*`) and validated with zod; a schema change marks the provider degraded without touching stored data.

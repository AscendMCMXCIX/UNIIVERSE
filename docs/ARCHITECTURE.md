# Architecture

UNIIVERSE is a single Next.js 16 application (App Router, TypeScript, Tailwind v4) with a PostgreSQL database. There are no microservices: background work runs as *jobs* inside the same codebase, triggered by any scheduler that can call a URL.

## Layers

| Layer | Location | Notes |
| --- | --- | --- |
| Domain | `src/domain` | Pure TypeScript, no I/O. Roles, tournament sequence, draft state machine, player eligibility, legal role assignments, statistics shrinkage, champion characteristics, composition model, recommendation engine, game plan. Everything here is unit tested. |
| Server | `src/server` | Database (Drizzle ORM), repositories, Riot static/API providers, pro-data providers, ingestion, aggregation, stats loader, jobs, scheduler, auth, server actions. |
| UI | `src/components`, `src/app` | Server components for pages, client components for interactive parts (draft room, champion picker, editors). |

Dependency direction is strictly UI → server → domain. The domain never imports from the server.

## Database

- Production: PostgreSQL (Supabase recommended) through `postgres-js`, `prepare: false` for pooler compatibility.
- Local/demo/tests: [PGlite](https://pglite.dev) (embedded Postgres) persisted in `./.data`, or in memory for tests.
- Migrations are generated by `drizzle-kit` into `drizzle/` and **embedded** into the app (`src/server/db/migrations.generated.ts`) so every instance migrates itself on first connection, serialised by a Postgres advisory lock. No separate migration step on deploy.

Main tables (see `src/server/db/schema`):

- `teams`, `players`, `player_champion_pools`, `lineups`, `lineup_slots`
- `champions`, `patches`, `champion_change_points`
- `drafts`, `draft_actions` (with the recommendation snapshot at the time), `draft_role_swaps`
- `tracked_summoners`, `match_fetch_queue`, `ranked_matches`, `ranked_participants`, `ranked_bans`
- `pro_games`, `pro_game_picks`, `pro_game_bans`
- `stat_periods`, `champion_role_stats`, `champion_ban_stats`, `champion_matchups`, `champion_synergies` – keyed by `(patch, source)`; history is never overwritten
- `data_refresh_status`, `job_runs`, `app_settings`

## Request flow in the Draft Room

1. The page loads the draft, its actions and the lineup snapshot (pools as they were when the draft started).
2. `recommendForDraft` builds the champion map (synced roster + curated profiles), loads the cached statistics provider for the current patch, and calls the domain `recommend()`.
3. Each ban/pick is a server action: validate against the sequence, persist the action (plus a snapshot of what was recommended), recompute recommendations, and when the draft completes, generate and store the game plan.

A recommendation takes about 50–100 ms; statistics are precomputed by the aggregation job and cached in memory per patch/stats version.

## Automation

`src/server/jobs/scheduler.ts` implements a *tick*: it runs every job whose interval has elapsed, in dependency order (static → ranked → pro → aggregate → integrity), within a time budget. Any scheduler can call `GET /api/jobs/tick` with `Authorization: Bearer $CRON_SECRET`. Individual jobs are available at `/api/jobs/<name>` and from the CLI (`pnpm job <name>`). Intervals live in `app_settings` and are editable in Settings.

Every job is idempotent and resumable: match ids are primary keys, aggregation marks matches in the same transaction that increments the counters, and a failing provider leaves the last-known-good data in place while the job is recorded as *degraded*.

## Team platform additions (session 2)

- **Accounts**: `users`, `sessions` (scrypt password hashes for everyone, a `must_change_password` flag and expiry for admin-issued temporary passwords, server-side sessions; roles owner/player — `coach`, `invites` and `activation_codes` are retired). Local development runs an implicit owner session; production requires `UNIIVERSE_AUTH_SECRET` and creates the owner through a one-time setup key.
- **Riot accounts**: `riot_accounts` (PUUID unique, Riot ID unique per platform), `account_champion_history`, `account_matches` (ledger so a match is folded exactly once), `account_mastery`; `src/server/accounts/sync.ts` is incremental and the `account-sync` job runs it in batches.
- **Series**: `series` (mode, event, opponent label, best-of, running score, status); `drafts.series_id`/`game_number` and `matches.series_id`/`game_number` tie games to it. Pure rules in `src/domain/series.ts`; the score is recomputed from recorded results (`src/server/series/repository.ts`).
- **Enemy names**: `drafts.enemy_players` and `matches.enemy_players` (optional names by role). The former scouting tables `opponent_teams` / `opponent_players` remain in the database but are no longer written or shown.
- **Draft formats and modes**: formats are data (`src/domain/draft/formats.ts`), custom ones live in `app_settings.draft_formats` and are embedded into each draft so history never changes.
- **Live drafts**: `drafts.version` (optimistic concurrency), `drafts.controller_user_id`, `draft_presence`; `GET /api/drafts/[id]/stream` is a server-sent-events feed that polls the version and presence.
- **Matches**: `matches` archive rows created on completion; the playbook (`src/domain/playbook`) is stored as drafted. Nothing reads the archive back into the engine.
- **Branding**: `app_settings.branding` (validated in `src/domain/branding.ts`), applied as CSS variables on the app shell. The UNIIVERSE mark, wordmark and backdrop ship in `public/brand/` (favicon and Apple icon are `src/app/icon.png` and `src/app/apple-icon.png`); the mark is shown wherever no custom logo is set, the wordmark and backdrop only on the sign-in, first-run and welcome pages (`src/components/auth/brand-frame.tsx`). The default accent is the brand cyan; a team can still override name, colour and logo in Settings.

## Authentication

Private by default. Members have their own accounts (username, unique case-insensitively; no email). Owners / Admins hold every permission; players hold configurable capabilities (`src/server/auth/permissions.ts`; see "Phase 3" below — the default Standard Player preset views everything, creates drafts and edits their own profile and Riot accounts). Draft-level rights are ownership, not a role: `canControlDraft` lets the draft's (or series') creator act and admins override; drafts from before ownership (no creator) are admin-controlled. Every server action calls `requireSession` / `requirePermission` / `requirePlayerEditor` or the draft/series/match ownership checks; pages hide what the viewer cannot do, but the actions are the real gate (tests/db/auth-actions.test.ts calls them with a player's cookie). The retired `coach` role and `draft_lead` flag were converted to Player by migration 0007, never to Admin.

**Account creation** (`src/server/riot/verify-identity.ts`, `src/server/auth/account-admin.ts`): the admin enters a username and a Riot ID; Riot's ACCOUNT-V1 must resolve it to a PUUID (names sent exactly as typed, URL-encoded Unicode) and the identity must not belong to another player. `createVerifiedPlayerAccount` then inserts the user (`setup_completed_at` null), the player profile and the Riot account with its PUUID in one transaction, then gives the account a temporary password; a profile archived by an earlier deletion is reused for the same Riot identity. Match history, mastery and proficiency follow in the background (`kickoffAccountSync`). The server action verifies again: a client cannot skip verification.

**Password sign-in** (`src/server/auth/password.ts`, `src/server/repositories/users.ts`): every account signs in with username + password (scrypt). Temporary passwords are 14 characters from a 54-symbol alphabet drawn with `crypto.randomInt` (≈80 bits), shown to the admin once, stored only as a hash, expire after 7 days and set `must_change_password`; issuing one deletes every session of that account. While the flag is set the session can only reach `/welcome`, where the player chooses a permanent password (typed twice; the server refuses reuse of the temporary one), which clears the flag and the expiry so the temporary password stops working; then the mandatory setup follows and resumes at the next sign-in if interrupted. Failed sign-ins are throttled per username and address (8 per 15 minutes). Activation codes from the earlier passwordless version were revoked by migration 0008; accounts that still have an older password keep it. Deactivation revokes every session; deletion archives the profile (history stays) and deletes the account. The last active admin can never be deactivated, deleted or demoted, and nobody can do that to themselves.

**Mandatory first-time setup** (`src/server/auth/onboarding.ts`, `/welcome`): primary role and 1–6 champions are required, a secondary role with up to 3 is optional; progress autosaves to `users.setup_progress`. Until `setup_completed_at` is set, the app layout redirects to `/welcome` and `requireSession` refuses every action except the two setup actions.

Sessions are rows in `sessions` (`src/server/auth/sessions.ts`): the browser holds an opaque HTTP-only cookie, the database its SHA-256 hash; every session ends 24 hours after sign-in, whatever its stored expiry, and activity does not extend it (`src/server/auth/config.ts`; no "remember this device", no override); logout deletes the row, a password change, deactivation or reset deletes every row of that user. `src/proxy.ts` sends anonymous visitors to `/login`; job endpoints use `CRON_SECRET`. Locally with no configuration the app runs as an implicit local owner (no login). In production the first visit shows a setup page that requires the one-time `UNIIVERSE_ACCESS_PASSWORD` setup key to create the owner; owners who lose their password use `/recover` with the same key.

**Admin Mode** (`src/server/auth/view-mode.ts`): owners default to the Player View and opt into Admin Mode through a preference cookie set by `switchViewAction`; the cookie only changes the navigation, every `/admin/*` page re-checks the owner role on the server. Player navigation is Team, Draft, Players, Matches, Overview, Trends and Settings; the Admin area is Users & Permissions, Players & Accounts, Competition, Data & Riot, Branding and System Health.

Sessions are rows in `sessions` (`src/server/auth/sessions.ts`): the browser holds an opaque HTTP-only cookie, the database its SHA-256 hash; every session ends 24 hours after sign-in, whatever its stored expiry, and activity does not extend it (`src/server/auth/config.ts`; no "remember this device", no override); logout deletes the row, a password change or reset deletes every row of that user. Signed-JWT cookies from before the sessions table are no longer accepted. `src/proxy.ts` sends anonymous visitors to `/login`; job endpoints use `CRON_SECRET`. Locally with no configuration the app runs as an implicit local owner (no login). In production the first visit shows a setup page that requires the one-time `UNIIVERSE_ACCESS_PASSWORD` setup key to create the owner; with `DATABASE_URL` or `UNIIVERSE_AUTH_SECRET` missing it refuses to run insecurely and explains what to set.

## Team, Players and My Overview

- **Team** (`src/server/team/overview.ts`, `src/components/team/lineup-overview.tsx`): the five lineup slots with the assigned player, their pool for that role and per-champion context read from stored history (`src/server/players/history.ts` resolves each `account_champion_history` bucket to a patch distance) and the proficiency lookup: ranked games and win rate on the current and previous two patches, proficiency tier. The swap dropdown lists Main players for the role and reveals Other players only when substituting; `setLineupSlotAction` requires `manage-lineup`.
- **Players** (`/players`, `/players/[id]`, `/players/[id]/edit`): the browse list (Main / Other), the read-only profile every member can open (roles, pools, Riot accounts, overview, collapsible proficiency detail; never passwords, sessions or infrastructure) and the editor for the profile's owner and admins. Roster administration (Add Player Account, password resets, account status, Main / Other) is the Admin → Players & Accounts page.
- **My Overview** (`src/domain/season-stats.ts`, `src/server/players/season-games.ts`, `src/server/players/overview.ts`, `src/components/players/player-overview.tsx`): plain counts over the per-match ledger (`account_matches`) for one season. Seasons come from the game version (`src/domain/season.ts`: 16.x = 2026; year-named patches like 26.20 are mapped to 16.20 by `canonicalPatch`). Games seen from two linked accounts count once (`dedupeGames`); modes are All supported games (Solo/Duo, Flex, Normal Draft/Blind, Swiftplay/Quickplay, Clash), Ranked Solo/Duo, Ranked Flex and Normal games. Mastery is summed across accounts with a breakdown (`combineMastery`). `?season=` and `?mode=all|solo|flex|normal` are GET parameters; no Riot request happens while rendering. Completeness: *Partial season* until every account's `history_backfill` is complete. `/overview` is the member's own view; teammates see the same component on `/players/[id]` (read-only; the journal lives under `/overview/blocks` and is private).

## Ranked Improvement journal (Solo Queue Blocks)

A private Solo/Duo journal per player, deliberately separate from the team's drafting data: nothing in it feeds the engine, proficiency or Match History, and no other member can read it.

- **Tables** (migration `0005`): `ranked_profiles` (one row per player: Champion 1–3, counter pick, the one-sentence focus), `ranked_blocks` (`player_id`, `number` unique per player, `status` active|completed, started/completed timestamps) and `ranked_games` (block, player, optional Riot account and match id, played-at, role, champion, enemy champion, result, main mistake, notes, link, optional `teammate_player_id`). Deleting a player removes their journal (cascade); deleting a tagged teammate only clears the tag (set null); unlinking a Riot account keeps imported games (set null). Indexes: games by player and date, by block, and a unique `(player_id, riot_match_id)` so a synced match is imported once.
- **Rules** (`src/domain/ranked-improvement.ts`): a block holds up to `BLOCK_SIZE = 6` games, may be finished earlier at its actual size, completes itself on the sixth game, and the next block takes the next number (`BLOCK 004`); one main mistake from a fixed list per game; links must be http(s). Dashboard and statistics are plain counts over the games that exist.
- **Authorization** (`src/server/ranked/owner.ts`, `src/server/actions/ranked.ts`): the owner is always the signed-in session's own `playerId`; no page or action accepts a player id. Every repository function (`src/server/ranked/repository.ts`) takes the owner first and filters on it, so a foreign block or game id is simply "not found". Tagging a teammate stores the id only; it grants nothing.
- **Import**: `listImportableMatches` reads the owner's own `account_matches` rows (queue 420, champion and result known, match id not yet journaled) and `importMatch` copies the facts (date, account, champion, enemy laner, result, role); the main mistake and notes are added by the player. Manual entry never depends on Riot.
- **Pages**: `/overview/blocks` (dashboard, ranked focus, current block with the thirty-second entry form, import list, simple statistics, recent blocks), `/overview/blocks/history` (paginated blocks) and `/overview/blocks/[id]`. The phone tab bar shows **Overview** (the journal is a subsection of it); Trends stays in the drawer and sidebar.

## Future-proofing

- No hard-coded patch, champion count or season: versions come from Data Dragon, champions from the synced roster, statistics periods from the data itself.
- New champions appear automatically with a *derived*, low-confidence characteristic profile until curated in `src/domain/champion-model/curated-data.ts`.
- Provider parsing is isolated per adapter (`src/server/riot/api/schemas.ts`, `src/server/pro/*`) and validated with zod; a schema change marks the provider degraded without touching stored data.

## Regions, Riot identity and labelled data

- `src/domain/riot-platforms.ts` is the only list of Riot League platforms (17 public servers, their labels and regional routing hosts). `RIOT_PLATFORMS` accepts `all`, platform ids or regional shorthands; everything else (API client, ingestion, selectors, coverage) reads this registry.
- `src/server/riot/api/rate-limiter.ts` keeps one sliding-window limiter per Riot host (`RateLimiterPool`), matching how Riot counts application limits; the client reports requests per host.
- `src/server/ingestion/ranked.ts` is region-scoped and bounded (stalest ladders refreshed in parallel, fair match-list scans per platform, one ingest worker per regional host) and records per-platform state in `region_status`; `src/server/ops/coverage.ts` turns that into the Global Data Coverage table and its warnings.
- `src/server/accounts/sync.ts` resolves Riot IDs with ACCOUNT-V1 (PUUID, Riot's spelling, active server), stores plain-language outcomes (`src/domain/account-status.ts`: Synced · Pending · Stale · Error) and never fails sign-up when Riot is down (`src/server/accounts/kickoff.ts` runs the first verification after the response).
- `src/server/proficiency/provenance.ts` builds the per-player RIOT DATA report (accounts, games analysed, current-patch games, per-champion proficiency with confidence, admin diagnostics, no PUUIDs); `src/domain/metrics.ts` is the glossary every labelled number and ⓘ tooltip reads from (`src/components/ui/metric.tsx`).
- The engine's `PickRecommendation.breakdown` (`src/domain/engine/picks.ts`) decomposes a pick into team fit, enemy interaction, player proficiency, current-patch strength, pro priority, realism and timing, and says when linked-account data changed the ranking versus pool order alone.

## Phase 2: Riot data, draft intelligence and match management

- **Season history** (`src/server/accounts/sync.ts`): each account sync reads every supported queue (420, 440, 400, 430, 480, 490, 700) newest first, then resumes older pages from the per-queue offset stored in `riot_accounts.history_backfill` until the season start, at most `ACCOUNT_SYNC_MATCHES_PER_RUN` (default 80) new matches per account per run; empty queues are rechecked every 12 hours. Statuses: Pending sync · Verified · Synchronising (season history still being collected) · Synced · Delayed · Failed (`src/domain/account-status.ts`).
- **Rate limits** (`src/server/riot/api/rate-limiter.ts`): the client adopts Riot's own `X-App-Rate-Limit` header (development, personal or production key alike) unless `RIOT_RATE_LIMITS` pins them.
- **Scheduler** (`src/server/jobs/scheduler.ts`): the tick runs version-check → account-sync (≤75 s) → ranked-discover (≤40 s) → pro-sync (≤40 s) → aggregate (≤60 s) → integrity (≤20 s) → ranked-ingest (the rest, minus a 30 s margin). Ingestion runs last because one fetch can wait on Riot's two-minute rate-limit window; when it stored games, aggregation runs once more straight after it (a few seconds), so new games reach the statistics, Trends and recommendations in the same tick. Ingestion round-robins the servers and ladder bands that share a Riot host (one worker per host). Ticks are started by GitHub (hourly), Vercel (daily) and visits (`src/server/jobs/background.ts`: a lease row lets at most one visit-started tick run per 30 minutes).
- **Proficiency** (`src/domain/proficiency`): queue-aware weights (Solo/Duo 1, Flex 0.9, Clash/other 0.85, Normal 0.6); normals add familiarity and practice but never the ranked performance baseline.
- **Enemy scouting** (`src/domain/scouting`): 0–5 Riot IDs, order-free; `inferEnemyRoles` assigns each name its most played role with a certainty that scales its pick-likelihood confidence.
- **Emergency picks** (`src/domain/engine/emergency.ts`): only when a player's whole pool for the role is banned or taken; about three champions plausible in the role (role prior ≥ 15 % or measured share ≥ 25 % over 300+ games), ranked by team need and patch strength with an unfamiliarity penalty; never written to a profile.
- **Quick Playbook** (`src/components/playbook/quick-playbook.tsx`, `/draft/[id]/playbook`): one screen at 1366×768 and larger; `?view=detail` shows the detailed analysis.
- **Match corrections** (`src/server/actions/matches.ts`): edit and delete for the draft's creator or an admin, checked on the server; a deleted record is archived (hidden, restorable by saving the draft again) and its series re-scored.
- **Read-only diagnostics jobs**: `data-audit` (anonymised Riot data coverage) and `engine-probe` (real lineup proficiency and whether it changes the engine's projected team), run from GitHub Actions → Data jobs.

## Phase 3: interface, permissions, accounts and branding

- **Capabilities** (`src/server/auth/permissions.ts`): owners hold everything; a player's capabilities are their custom set, else their preset (`permission_presets`), else the default preset. `hasPermission` is checked in every server action and page (`requirePageAccess` in `src/server/auth/page-access.ts`); navigation only mirrors it (`src/lib/nav.ts`). `manage-users` (accounts, passwords, permissions) is owner-only and cannot be granted. Migration 0012 added the presets, `users.permission_preset_id`, `users.custom_capabilities` and `user_avatars`.
- **Account self-service** (`src/server/repositories/profile.ts`, `src/server/actions/account.ts`): case-insensitive unique username changes, password rules for new passwords (`src/domain/password-policy.ts`), profile pictures cropped in the browser and checked by their bytes on the server (`src/server/images.ts`), served members-only from `/api/avatars/[userId]`.
- **Riot ID changes** (`src/server/accounts/change-riot-id.ts`): the scheduled sync re-reads the Riot ID by PUUID (`riot_accounts.riot_id_checked_at`); a typed change renames the same PUUID, asks before replacing a different account and refuses another player's.
- **Profile editing** (`src/components/profile`): one champion selector (`src/components/champions/champion-grid.tsx`, role filter from `src/server/champions/picker.ts`), a sortable pool (`sortable-pool.tsx`) and autosave (`use-profile-autosave.ts` → `saveProfilePatchAction`), which merges quick edits, sends one request at a time and refuses a stale version (`players.updated_at`, row locked while checking).
- **Draft setup and room** (`src/app/(app)/draft/page.tsx`, `src/components/draft`): the setup reads the lineup through `src/server/team/setup-lineup.ts`; enemy players are stored at creation only (the old editing action is gone). The room is one client component laid out as champion select; the recommendation strip and analysis read the same `RecommendationResult` as before (no engine changes).
- **Branding** (`src/domain/branding.ts`, `src/server/repositories/branding.ts`): names and colours in `app_settings`; images in `brand_assets` (migration 0013, which copies a logo that used to be stored inline) served from `/api/branding/<kind>` with versioned, immutable URLs and a sandboxing CSP. Animated GIFs keep a still frame (`<kind>-static`) drawn in the browser for favicons, reduced motion and the in-app backdrop. Colours become CSS variables (`brandThemeCss`), only after WCAG contrast checks pass.
- **Status pages** (`src/domain/data-health.ts`, `src/domain/system-health.ts`): every label is derived from collected data or a measurement on the request; nothing is Healthy by default.
- **Notifications** (`src/components/ui/toast.tsx`): results of actions; field-level problems stay beside their field. Sensitive actions confirm in `ConfirmDialog`.
- **Styling helpers** (`src/lib/cn.ts`): `withDefaults` lets a caller's size and colour classes replace a component's defaults (there is no class-merging library).

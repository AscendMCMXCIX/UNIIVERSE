# Data pipelines

UNIIVERSE collects two kinds of data: Riot's static game data (champions, skins, patches) and the linked players' own Riot accounts (games, ranks, mastery). Every pipeline follows the same shape: **external provider → adapter → validation → normalised tables**. Provider quirks never reach the pages.

## Riot static data (Data Dragon)

`version-check` (hourly) fetches `versions.json`. When the newest version differs from the stored current patch it downloads `champion.json` and the per-champion files, upserts champions (new ones get `firstSeenVersion`) and their skins, opens the new patch as *current* and clears caches; item, summoner spell and rune names for the match history follow once per game version. If Data Dragon is unreachable and the database is empty, an offline fixture seeds the roster so development can continue; it is replaced by the first successful sync.

## Riot requests

Riot rate-limits each host separately, and the client keeps one sliding-window limiter per host (`RateLimiterPool`, `RIOT_RATE_LIMITS`, default dev/personal-key limits 20/1 s and 100/120 s per host), honours `Retry-After` on 429, backs off exponentially on 5xx and retries a bounded number of times. Jobs stop at their time budget and resume on the next run, and no request waits past it: every caller with a budget gives its client that deadline, and no request is sent after it or one that would have to wait beyond it (a full window, a `Retry-After`). That is a stop for time like any other, not a failure: the account stays as it was (never Pending for it, and not marked synced when a due current-season list was left unread before any was read), the key's status is untouched, and what the run stored is kept. A request that met a network error or a 5xx and cannot be tried again in time is a failure, not a stop for time: Riot did fail, so the account waits as Pending with Riot's reason and the run is degraded. That holds when one of the sync's best-effort lookups (the Riot ID check, the active server, rank, mastery) met such a failure, no later lookup succeeded, and time then ran out before any season list was read. On a client that retries, a 429 whose Retry-After leaves no time is a stop for time (a Refresh does not retry: a 429 on its list request is reported as Riot rate-limiting, as before), and a failed match request inside the history stops that page, as before. Servers are resolved through the single platform registry in `src/domain/riot-platforms.ts` (17 public League servers, no Chinese servers); `RIOT_PLATFORMS` only names the server the key check asks.

## Linked Riot accounts (`account-sync`)

Players link Riot accounts by Riot ID (`GameName#TAG`, stored exactly as typed). ACCOUNT-V1 requests go to the americas, asia or europe routing value (`accountRegionFor` in `src/domain/riot-platforms.ts`): Riot does not serve that API from the `sea` host that carries OCE and South-East Asian match data, and asking it there answers 403, which is indistinguishable from a rejected key. Resolution is real and in this order: ACCOUNT-V1 `by-riot-id` → PUUID (the canonical identity; Riot's own spelling of the name is adopted), then ACCOUNT-V1 `region/by-game/lol/by-puuid` → the server the account actively plays on, which replaces the sign-up region selection (`platform_source = riot`); if that lookup is unavailable the selected server stays (`platform_source = user`, OCE by default). Sign-up never waits for Riot: accounts are inserted as `never`, a best-effort verification runs right after the sign-up response (`kickoffAccountSync`), and anything Riot could not answer is stored as `pending` with a plain-language reason and retried by the job.

Every tick (`account-sync` is due every 15 minutes) works through the linked accounts most urgent first: new or failing links (retried with back-off: 5 minutes after the first failure, doubling per attempt up to 6 hours), accounts still collecting this season's history (every run until complete), accounts of active players (main group, or signed in during the last week) not refreshed for 45 minutes (`ACCOUNT_SYNC_ACTIVE_AGE_MINUTES`), then everyone else after 3 hours (`ACCOUNT_SYNC_MIN_AGE_MINUTES`); only player accounts are refreshed; `ACCOUNT_SYNC_BATCH` and `ACCOUNT_SYNC_PENDING_BATCH` bound a run so failing links never starve the rest. Opening a player's overview, profile or Riot settings also refreshes that player's due accounts in the background (about 40 seconds, 60 matches, a two-minute lease per player; like the scheduler, it claims each account's sync lease first, dated from the slice's start, and leaves an account another sync claimed in the last 100 seconds to that sync, longer than a tick's account sync can hold one; a slice that found every due account held gives its two-minute lease back, and the first sync after sign-up gives each account back when it is done with it, so the page's next render carries the history on), and the open page checks a short version of its data (every 10 seconds while that refresh runs, every 30 while older games are still being added, less and less often otherwise, never while the tab is hidden) and reads itself again only when it changed (`docs/ARCHITECTURE.md`, "Pages that update themselves"), so a slice's games appear while it is watched. The page renders again only when its data changes, so once a slice is over the next one starts with a later change or the next visit, and the scheduler (every run until the history is complete) does the rest. Per account it resolves the PUUID when unknown, confirms the server, refreshes rank and champion mastery, and collects the whole current season for every supported queue (Ranked Solo/Duo 420, Ranked Flex 440, Normal Draft 400, Blind 430, Swiftplay 480, Quickplay 490, Clash 700): the newest page first, then older pages resumed from `history_backfill` until the season start (1 January, or the day the season's first patch was seen if that came earlier; games are assigned to seasons by patch, so no season date is assumed), bounded per run so the tick stays inside its time budget. A game another linked account has already stored is folded from its stored record (`match_details`, reduced in the database to what folding reads) instead of being fetched from Riot again (`accounts/fold-input`); the record is used only when it lists the account, so a record stored under an earlier Riot key, or one of a game Riot no longer serves, sends the sync back to Riot. The production audit of 3 Nov 2026 counted 4,951 stored account games for 3,670 distinct games: about one match request in four had been for a game another account had already fetched. `account-sync`'s summary reports `fromRecords`. A game's role is Riot's team position, or its individual position when the team position is empty (as the stored record has always kept it), whichever account fetched it first. Each match is folded exactly once into `account_champion_history` (games/wins/KDA per champion, role, queue group and patch) through the `account_matches` ledger, so re-running or overlapping windows never double count. Nothing listed is skipped for good: when a run stops partway down a queue's newest page (its per-run limit, the time budget or a failed request) with games below the ones it stored still to fetch, the queue is marked for a rescan (`history_backfill` queue `rescan`), and once a later run completes that page, the older pages are read again from there, because new games arriving meanwhile could push the rest past the newest page, into the part of the list already read (a long gap between syncs; one list request per hundred stored games, which cost nothing else). Until then the queue keeps its state: a finished queue stays finished, so a game that fails every time holds nothing back beyond what it did before. A listed game for which Riot gives the same answer every time (404, or a reply that is not a readable match) is stored as a ledger row without a champion, like a remake (`game_creation` 0: Riot gave no time), so its queue still finishes. That happens only when a newer game of the same list reads in that run (if none was fetched, a stored one is read again first: the nearest folded game above it, or the queue's newest folded game), so a change in Riot's format or a fault in UNIIVERSE's own reading that breaks every game records nothing; the newest game of a queue, which Riot may still be preparing, is asked for again until a newer one has been read. The limit: a fault that breaks only some games (older ones, say) while newer games still read records those games as unavailable, and once one game on a page is recorded the rest of that page's refused games are recorded without another check. To collect them again after such a fault is fixed, delete the rows with `champion_id IS NULL AND game_creation = 0` and reset `history_backfill` for the accounts concerned (a one-off repair to propose with a rollback, not something the sync does). Riot's servers failing, the network and the rate limit are never recorded: a later run tries again. A game on a champion the champions table does not have yet (a new champion, before `version-check` has the Data Dragon version with it) is not stored, so a later run folds it once the champion is there; after three days it is stored without a champion like a remake, so a champion that never appears costs at most three days of one request per run. Several accounts of one player are combined by the proficiency service; a Riot ID that resolves to a PUUID already linked (a renamed account) is flagged as a duplicate and never counted twice. Demo accounts (label `demo`) are never synced. Once the current season is complete, spare budget collects the previous season the same way (`history_backfill.previous`), so last season can be shown with real numbers; older seasons are not collected. Sync states shown to players: Updating (being verified, or first games on the way) · Catching up on history (recent data in, older games of the season being added automatically) · Up to date · Delayed (no refresh for 6 h, or Riot unavailable; retried automatically) · Needs attention (Riot ID not found, duplicate), each with a sentence and "Last updated". "Retry sync" appears only for Delayed and Needs attention. Unlinking an account deletes its rows. A run in which any account it tried could not be synced for a reason Riot or the network caused is recorded as *degraded*, with the count in its error (never a Riot ID), so Admin → Data & Integrations shows it. An account that needs a person (a duplicate, an erased person, a Riot ID Riot does not know) is shown on its player's Riot Accounts tab and does not make every run degraded.

Raw facts (`riot_accounts`, `account_champion_history`, `account_mastery`) stay separate from the derived proficiency (`src/domain/proficiency`): games, recent games, games this patch, role usage, last played, mastery and results become a 0–1 score, a confidence and a tier (Main · Comfortable · Familiar · Few games · Out of practice · Not played; revision 2, see `docs/CHAMPION_EXPERIENCE_LABELS.md`). Proficiency never changes the pools; it rates the champions in them on Team Overview and the profile. Each player's profile shows the per-champion table with provenance (accounts, games analysed, current-patch games, last sync); the Owner sees raw sync diagnostics.

`account_matches` also keeps per-match facts (queue, champion, role, result, enemy champion in the same position, patch, duration), which Match History, Played Together and possible groups read without another Riot call.

## Rank readings and LP per game (`rank-watch`)

A linked account's rank is read from LEAGUE-V4 (one request answers Solo/Duo and Flex) by account sync and by the rank watch. `rank_snapshots` keeps one row per change; an unchanged reading moves the last row's `confirmed_at` on (migration 0065), under a per-account-and-queue lock, so overlapping runs never duplicate a reading and a slow answer never moves one back. The rank watch (`src/server/jobs/rank-watch.ts`, in every tick, interval 5 minutes, and callable on its own at `/api/jobs/rank-watch`) reads the accounts that played ranked in the last 30 days every run and the others about hourly; at most 40 accounts a run, half of each rate-limit window, no retries, and a full limit or a refused key ends the run. A game's LP is never stored: it is worked out when a page shows it, from the readings around it (`src/domain/lp-attribution.ts`; the rule and its limits in [RANKED_PROGRESS.md](RANKED_PROGRESS.md)). `rank-audit` reports what the readings prove on real data, read-only.

## Ranks of a match's players

LEAGUE-V4 (`/lol/league/v4/entries/by-puuid/{puuid}`, the match's server) is asked about the other players of the members' games, and each answer is kept in `last_known_ranks` (both ranked queues, `UNRANKED` for a queue with no entry, `source` "match lookup"), at two moments:
- **After a game is collected** (the `rank-checks` job, in every scheduler tick after `account-sync`, due every 15 minutes, at most 15 s): the players of the members' games of the last 7 days with no check since that game ended, newest game first, 30 a run, so every recent card and scoreboard has the ranks around its game whether or not anyone opens it. It uses at most 600 of the day's checks and half of each rate-limit window: when its half of Riot's one-second window is full (about ten requests), it waits for the window to turn over, within its 15 s, and it leaves the rest to the next run when a wait gets nobody through (a longer window is full).
- **When a member opens a match**: its players with no check in the last 3 days, or none since a game of the last 7 days ended.

Members are never checked this way: their own sync reads their rank, and their rank history (`rank_snapshots`) gives their rank going into each game. At most 1,000 checks in any 24 hours across the site, half of each rate-limit window of that server (account sync keeps the other half), never a queued request, no retries. `data-audit` → `participantRanks` reports the coverage and the checks per day. Details: `src/server/players/participant-ranks.ts`, `docs/RIOT_COMPLIANCE.md` → Ranks in completed matches.

**Erased people** (`docs/PRIVACY.md`). The sync keeps the people whose personal data was erased out of everything it stores, through the erasure records (`erasureFilter`, `src/server/privacy/ledger.ts`):
- An erased person's own accounts are refused, before and after the PUUID is resolved, and logged only as `account 1a2b3c4d`.
- In anyone else's games they become a "Removed player": in `match_details`, in the figures and timeline backfills, and as a lane opponent (`enemy_champion_id`).
- They are matched by PUUID, or by Riot ID when a new API key changed the PUUIDs; a PUUID learned that way is added to their record.
- Sync log lines name accounts by a short id, never a Riot ID.

## Health and self-monitoring

`data_refresh_status` records each job's last start/success/failure, error, duration and consecutive failures. Admin → Data & Riot and `/api/health` surface warnings when a pipeline is stale (the version check silent for 26 hours) or failing repeatedly. A run killed before it finished (a function timeout, a crash) counts as a failed run: the next run of the job, starting once it has said "running" for 15 minutes, records it (one more consecutive failure, `last_failure_at`, "Run never finished (process was interrupted).") and closes its `job_runs` row as failed; until then a run past those 15 minutes already counts as failed in the warnings and `/api/health`. The `integrity` job (daily) unsticks job states left running by an interrupted process the same way (counted as a failed run) and closes every `job_runs` row left open for over 30 minutes, deletes sign-in sessions a week after they ended and prunes failed sign-ins older than the throttling window, in bounded batches. It also re-applies the personal-data erasure records to anything stored in the last two days, as a safety net, and reports a degraded run when a record was made under another `UNIIVERSE_AUTH_SECRET`. `erasure-reconcile` (on demand only) re-applies them to the whole database, after a restore (`docs/BACKUPS.md`).

## Retired tables (Meta & Trends, removed 2026-10-19)

Meta & Trends (Solo Queue Meta, Duo Synergies, Pro Play) collected high-Elo ranked games from every public server and professional games from Leaguepedia, and aggregated them into pick, ban, matchup, synergy and draft-slot statistics. The feature and its jobs (`ranked-discover`, `ranked-ingest`, `aggregate`, `pro-sync`) were removed; nothing writes these tables any more:

| Tables | Held | Still read by |
|---|---|---|
| `ranked_matches`, `ranked_participants`, `ranked_bans`, `match_fetch_queue`, `region_status` | Collected high-Elo games and the collection queue | nothing |
| `stat_periods`, `stat_region_periods`, `stat_rank_periods`, `champion_role_stats`, `champion_ban_stats`, `champion_matchups`, `champion_synergies`, `pro_pick_slot_stats` | Aggregated statistics | nothing |
| `pro_games`, `pro_game_picks`, `pro_game_bans` | Professional games | nothing |
| `champion_change_points` | Detected champion reworks (discounted old statistics) | nothing |
| `tracked_summoners` | High-Elo ladder players | nothing: migration `0048` copied the ranks Match History shows for other players into `last_known_ranks` |

**Migration `0062_retire_meta_trends_tables`** dropped 12 of them on 4 Nov 2026 (#86, audit decision 2): `ranked_matches`, `ranked_participants`, `ranked_bans`, `match_fetch_queue`, `champion_role_stats`, `champion_ban_stats`, `champion_matchups`, `champion_synergies`, `pro_pick_slot_stats`, `pro_games`, `pro_game_picks` and `pro_game_bans`, about 206 MB. It merged after a verified backup that holds them (`docs/BACKUPS.md`; the 2 Nov copy, kept until 30 Nov 2026, is the last weekly copy with them) and production checks that nothing read them (Data jobs `db-usage`). Recovery: `pg_restore --table` from that backup, then revert the change.

The rest (`region_status`, `champion_change_points`, the `stat_*_periods` tables and `tracked_summoners`) stay defined in `src/server/db/schema` so `drizzle-kit generate` never emits a `DROP`. Dropping them deletes the collected global data for good, so it is a separate migration that needs the owner's approval; it never touches user, team, champion or match records (`account_*`, `match_details`, `champions` and the rest stay). Match History's last-known ranks no longer depend on any of them (`last_known_ranks`, migration `0048`). Old status rows of the retired jobs stay in `data_refresh_status` and `job_runs` and are hidden (`RETIRED_JOB_KEYS` in `src/server/ops/refresh-status.ts`).

**Checking a drop against production first.** Data jobs `db-usage` reports `retired`: for these tables and the removed Draft feature's (`docs/ARCHITECTURE.md`, "Draft removed"), each one's rows, reads (sequential and index scans) and writes since the statistics were last reset (`statsReset`); the Draft's two columns and six enum types; Riot accounts of the legacy opponent type; and anything outside them that depends on them (foreign keys, views, columns of a retired type, publications). A drop merges only after a verified backup and when two runs a day apart show no new reads or writes and no dependent other than the `riot_accounts` foreign key that goes with its own column. Afterwards the same report shows each of them as gone.

## Dropped tables (Clash Scout, retired 2026-10-23)

Clash Scout was removed (`docs/CLASH_SCOUT.md`). Its pages, actions, Riot requests and its on-demand `lab-benchmark` job went first; migration `0064` then dropped its two tables, after the owner had verified a recent backup:

| Tables | Held |
|---|---|
| `clash_scouts` | The scouts the team saved: the opponents' names, ranks, champion figures and mastery read from Clash's screenshots, and the Riot ID and PUUID of each opponent a member verified |
| `clash_scout_accounts` | The verified PUUIDs of each saved scout |

The same change removed their schema (`src/server/db/schema/clash.ts`) and the code that cleared erased people from them (permanent erasure and its reconciliation). `db-usage` keeps listing them among `retired`, reported as gone. Old `lab-benchmark` status rows are hidden like the other retired jobs' (`RETIRED_JOB_KEYS`). Recovery, if ever needed: `pg_restore --table` from that backup, then revert the change.

# Data pipelines

UNIIVERSE collects two kinds of data: Riot's static game data (champions, skins, patches) and the linked players' own Riot accounts (games, ranks, mastery). Every pipeline follows the same shape: **external provider → adapter → validation → normalised tables**. Provider quirks never reach the pages.

## Riot static data (Data Dragon)

`version-check` (hourly) fetches `versions.json`. When the newest version differs from the stored current patch it downloads `champion.json` and the per-champion files, upserts champions (new ones get `firstSeenVersion`) and their skins, opens the new patch as *current* and clears caches; item, summoner spell and rune names for the match history follow once per game version, and so do the champions' abilities (next section). If Data Dragon is unreachable and the database is empty, an offline fixture seeds the roster so development can continue; it is replaced by the first successful sync. With `DDRAGON_VERSION` set (only the browser tests' server sets it, `playwright.config.ts`; never production), the newest version is that one: `DataDragonProvider.fetchVersions` returns it alone once `versions.json` lists it, so the champions, skins, patch, item names and abilities all come from that version, and the run's log says it is pinned. A pin that is not a version, or one `versions.json` does not list, fails the way an unreachable Data Dragon does (the offline fixture on an empty database, otherwise the stored data kept and the run degraded with the reason), never reading another version instead (docs/MATCHUP_INTEL.md, "What the browser tests pin"). What resolves a version follows from that: the version check reads the provider's; the item, spell and rune names, the abilities and the champion portraits use the version it stored; splash art has no version in its address; a match's item icons use the match's own game version; and the by-hand `skin-audit` diagnostic reads `versions.json` itself, as it only runs against production, which is never pinned.

## Champion abilities (Matchup Intel)

Matchup Intel shows each champion's abilities with their base cooldowns (`src/domain/matchup-intel/`). The roster-wide part comes from Data Dragon, which is static data Riot publishes before any game; nothing is read from a game in progress.

**Source.** Each champion's Data Dragon file (`champion/<id>.json`), the same files the version check reads for skins (`src/server/matchup-intel/abilities.ts`, `compactChampionAbilities`):
- The passive becomes P and the four spells Q, W, E, R. For each: the name, the icon (`image.full`), the ranks (`maxrank`; 1 for the passive), the base cooldown array as Riot gives it, and Riot's short description with its markup removed (never a source of numbers).
- A passive has no cooldown in Data Dragon (an empty array: "not in Riot's data", never "no cooldown"). An all-zero array is a placeholder (20 spells at 16.22.1).
- `maxammo` above 0 means charges (24 spells at 16.22.1; 10 more have `"0"`, which is none). The array is then the time between casts, not the recharge.
- A short hash of Riot's whole text for each ability (`riotTextHash`: the first 16 hex digits of SHA-256 over its raw `description` and, for a spell, its raw `tooltip`), stored as `textHash`, never the text. It tells the page when Riot's text has changed since the facts drawn from it were reviewed, which then hides them (docs/MATCHUP_INTEL.md, "Facts from Riot's text"). Rules format 2 (18 Nov 2026) added it.
- Never read for their words or numbers: `tooltip` (hashed only, never stored or shown), `leveltip`, `effect`/`effectBurn`, `vars`, `datavalues`, `range`/`rangeBurn`, `costType`/`resource`, nor `maxammo` as a recharge time.

**Stored** in `app_settings` "champion_abilities": `{ format, version, updatedAt, champions: { <id>: { championId, version, format, abilities } } }`. Each champion keeps its own version (an earlier one when it could not be read since) and its own `format`, the rules' revision that made it (`ABILITY_RULES_FORMAT`). A record made under other rules is read again on the next run, and kept until that read succeeds. The top-level `format` is the rules of the last write. Format 2 (Matchup Intel's redesign, 18 Nov 2026) adds `textHash` to each ability: the first run after it deploys reads all 173 champions once, as a change of rules does (about 2.3 MB from Data Dragon, 6 files at a time, within the run's 30-second limit or over the next runs), and until a champion is read again its record has no hash, so its facts from Riot's text show only on the very version they were reviewed against. The hashes add about 26 KB to the stored document (865 of 29 bytes; the offline copy went from 287,242 to 313,192 bytes).

**When it refreshes.** In `version-check`, after the champion sync, in its own `try` (a failure is logged and the rest of the run goes on):
- On a new version it uses the detail files the champion sync has just read: no extra request.
- Otherwise it reads only the champions whose record is missing, is from another version or was made under other rules, or every champion while the offline copy is stored (the first run after this was deployed reads all 173 once). Those files are requested 6 at a time with the provider's 15-second timeout, and none after the job's deadline or 30 seconds; the rest wait for the next run.
- With the version unchanged and nothing missing it is one statement. It reads the stored document once (a materialised CTE) and sends back a few hundred bytes: about 5 ms of database time with 173 champions on PostgreSQL 16 (4–6 ms measured, 102 buffers). Checking each champion against the stored row directly made PostgreSQL fetch it from TOAST and decompress it about 690 times: about 0.5 s and 11,000 buffers every hour. `tests/db/matchup-intel-abilities.test.ts` keeps the statement under 1,000 buffers with the whole roster stored.
- `static-sync` (forced) reads every champion again.
- The job's summary has an `abilities` entry with counts only, never a champion's name: version, source, stored, refreshed, kept from earlier, failed, deferred, files requested, degraded.

**On failure.** A champion whose file cannot be read, or is not in the expected shape, keeps its earlier record (after a change of rules too) and is tried again on the next run. When more than 10% of the roster cannot be read, nothing is written: the stored abilities stay (last known good), the rest of the files are not requested in that run, and the run is degraded with a counts-only message, which Data health shows as a warning. A lasting failure (a format Riot changed, a path that refuses) therefore costs each hourly run the files it takes to pass 10%, not the whole roster: 18 to 23 of 173 when every one fails (the 18 that decide it, and up to 5 already in flight). A path that times out instead is bounded by the 30-second limit, and such a run is not marked degraded unless more than 10% of the roster failed within it.

**Reading.** `loadChampionAbilities` reads only the champions asked for that are on the roster (the cached champion list): the record at `value->'champions'->'<id>'`, with the stored document read once. Those not cached go in one statement (about 2–3 ms for a matchup of two), and each is kept 10 minutes per instance (cleared by a sync that writes). An id is checked against `^[A-Za-z0-9]{1,40}$` before anything else, and one that names no active champion is neither read nor cached, so ids taken from a URL cannot fill an instance's memory. A champion with nothing stored is null; so is one whose stored record is not in the shape the page reads, which the result names in `unreadable`, so the page says it could not be read rather than that nothing is stored. Each record carries its own Data Dragon version, which is the one for its labels, icon URLs and freshness: after a failed read, two champions can differ, and the page judges and labels each by its own (an older one is named in its stale notice, and the footer gives both versions). The result's `version` is the version every returned record shares, or null when they differ or none is returned; `offline` names the records that came from the committed offline copy (below), which the page labels as that. A page never asks Riot.

**Offline.** Where the server cannot reach Data Dragon (this development sandbox, a machine without network), a committed copy stands in: `src/server/riot/fixtures/champion-abilities.fixture.json` holds every champion's abilities at Data Dragon 16.22.1 (173 champions). Where it can, the demo reads Data Dragon as production does. CI's browser tests run the in-memory demo with an open network and Data Dragon pinned to the version the curated notes were checked on (`DDRAGON_VERSION` = `E2E_DDRAGON_VERSION`, 16.22.1, `e2e/ddragon-version.ts`), so its first static sync stores that version's champions and, from the same detail files, its abilities, whatever Riot has shipped since; the copy is stored there only if those files could not be read, and the browser test that asserts the footer's "Riot Data Dragon 16.22.1 (patch 26.22)" then fails. A browser test of Matchup Intel may therefore read that version's numbers and labels; one that rests on a number moves with the pin when the notes are re-checked (docs/MATCHUP_INTEL.md, "When a patch changes them").
- It is built by `scripts/matchup-intel/build-ability-fixture.mjs` (`--from championFull.json` or `--version 16.22.1`, `--check` to compare) with the same rules in plain Node (the text hashes included), together with `tests/fixtures/ddragon-16.22.1-ability-digest.json`: Data Dragon's own numbers for every champion (each spell's id, `maxrank`, `cooldown` and `maxammo`, as Riot gives them). `src/server/matchup-intel/abilities.test.ts` holds the script and the app to the same results, and the copy's spell ids, ranks, cooldowns and charges to the digest for all 173 champions, in CI. With `CHAMPION_FULL_JSON` set it also runs every champion through the rules and checks both committed files byte for byte.
- It is stored, labelled `source: "fixture"` (each champion keeps version 16.22.1), when the champions come from the offline fixture, and by the demo's bootstrap when no abilities are stored. The page says so ("Offline copy of Riot Data Dragon 16.22.1", and that the game's current patch is not known).
- It never replaces abilities read from Data Dragon. The first real sync replaces it whole: a champion that cannot be read is left out until the next run, never mixed in.

**Facts from Riot's text.** Not a pipeline: the reviewed kinds of mechanic drawn from Riot's descriptions and tooltips are committed files, one per champion (`src/server/matchup-intel/riot-text/`), written by `scripts/matchup-intel/import-riot-text.mjs` from a completed review and Data Dragon's `championFull.json` read from a file (it downloads nothing), and loaded on the server only for the champions on the page that have no checked notes (docs/MATCHUP_INTEL.md, "Facts from Riot's text"). No job writes them. Imported on 19 Nov 2026: 173 files (Data Dragon 16.22.1, 1,112 facts), each ability pinned to `riotTextHash`, so a later Data Dragon version whose text differs hides that ability's facts until a new review is imported.

**Cost.** One write of about 270 KB per game version (117 KB on disk), plus about 26 KB of text hashes since rules format 2 (not re-measured on disk). The hourly check when nothing changed: one statement, a few hundred bytes back and about 5 ms of database time. Reads of 1.2–2.6 KB per champion shown (about 0.15 KB more with its five hashes; about 2–3 ms for a matchup of two), cached. The first fill requests about 2.3 MB from Data Dragon once, and compacting the roster takes about 6 ms of CPU. Measured figures are in `docs/HOSTING_USAGE.md`.

## Riot requests

Riot rate-limits each host separately, and the client keeps one sliding-window limiter per host (`RateLimiterPool`, `RIOT_RATE_LIMITS`, default dev/personal-key limits 20/1 s and 100/120 s per host), honours `Retry-After` on 429, backs off exponentially on 5xx and retries a bounded number of times. Jobs stop at their time budget and resume on the next run, and no request waits past it: every caller with a budget gives its client that deadline, and no request is sent after it or one that would have to wait beyond it (a full window, a `Retry-After`). That is a stop for time like any other, not a failure: the account stays as it was (never Pending for it, and not marked synced when a due current-season list was left unread before any was read), the key's status is untouched, and what the run stored is kept. A request that met a network error or a 5xx and cannot be tried again in time is a failure, not a stop for time: Riot did fail, so the account waits as Pending with Riot's reason and the run is degraded. That holds when one of the sync's best-effort lookups (the Riot ID check, the active server, rank, mastery) met such a failure, no later lookup succeeded, and time then ran out before any season list was read. On a client that retries, a 429 whose Retry-After leaves no time is a stop for time (a Refresh does not retry: a 429 on its list request is reported as Riot rate-limiting, as before), and a failed match request inside the history stops that page, as before. Servers are resolved through the single platform registry in `src/domain/riot-platforms.ts` (17 public League servers, no Chinese servers); `RIOT_PLATFORMS` only names the server the key check asks.

## Linked Riot accounts (`account-sync`)

Players link Riot accounts by Riot ID (`GameName#TAG`). An administrator's Add Player Account and a profile's Riot Accounts tab link one only once Riot knows it: both ask ACCOUNT-V1 `by-riot-id` first, with the same messages (`lookupRiotId` in `src/server/riot/verify-identity.ts`), and store the account under Riot's spelling with its PUUID. A Riot ID Riot does not know is refused, and so is one Riot cannot be asked about right now (no key, a refused key, a rate limit, Riot down or unreachable), with a message to try again: neither links anything unchecked. (Until November 2026 the Riot Accounts tab stored any well-formed Riot ID as typed and left it to the first sync.) The Owner's setup page and the Owner's one-time profile completion still store a Riot ID exactly as typed, for the first sync to resolve. ACCOUNT-V1 requests go to the americas, asia or europe routing value (`accountRegionFor` in `src/domain/riot-platforms.ts`): Riot does not serve that API from the `sea` host that carries OCE and South-East Asian match data, and asking it there answers 403, which is indistinguishable from a rejected key. Resolution is real and in this order (an account linked with its PUUID starts at the second step): ACCOUNT-V1 `by-riot-id` → PUUID (the canonical identity; Riot's own spelling of the name is adopted), then ACCOUNT-V1 `region/by-game/lol/by-puuid` → the server the account actively plays on, which replaces the sign-up region selection (`platform_source = riot`); if that lookup is unavailable the selected server stays (`platform_source = user`, OCE by default). Sign-up never waits for the first sync: accounts are inserted as `never`, a best-effort sync runs right after the sign-up response (`kickoffAccountSync`), and anything Riot could not answer is stored as `pending` with a plain-language reason and retried by the job.

Every tick (`account-sync` is due every 15 minutes) works through the linked accounts most urgent first: new or failing links (retried with back-off: 5 minutes after the first failure, doubling per attempt up to 6 hours), accounts still collecting this season's history (every run until complete), accounts of active players (main group, or signed in during the last week) not refreshed for 45 minutes (`ACCOUNT_SYNC_ACTIVE_AGE_MINUTES`), then everyone else after 3 hours (`ACCOUNT_SYNC_MIN_AGE_MINUTES`); only player accounts are refreshed; `ACCOUNT_SYNC_PENDING_BATCH` (10) bounds a run's new and failing links and `ACCOUNT_SYNC_BATCH` (12) the rest, each share apart, so links waiting for Riot never starve the rest, however many there are. Opening a player's overview, profile or Riot settings also refreshes that player's due accounts in the background (about 40 seconds, 60 matches, a two-minute lease per player; like the scheduler, it claims each account's sync lease first, dated from the slice's start, and leaves an account another sync claimed in the last 100 seconds to that sync, longer than a tick's account sync can hold one; a slice that found every due account held gives its two-minute lease back, and the first sync after sign-up gives each account back when it is done with it, so the page's next render carries the history on), and the open page checks a short version of its data (every 10 seconds while that refresh runs, every 30 while older games are still being added, less and less often otherwise, never while the tab is hidden) and reads itself again only when it changed (`docs/ARCHITECTURE.md`, "Pages that update themselves"), so a slice's games appear while it is watched. A slice's last write lands while its own two-minute lease still stands, so the render it causes starts nothing. Since 6 Nov 2026 the player's version also changes once that lease is over, while an account is still adding this season's history, no other sync holds it, and the last slice did not read it without moving it on (`src/server/ops/freshness.ts`). So a profile left open renders again and starts the next slice, and a new account's history fills in while it is watched. An account the last slice read and could not move (a game Riot answers 5xx for every time; the slice lists it in its lease) waits for the next visit or data change instead of a slice every two minutes; an account the slice did not try (another sync held it, or time ran out first) is never listed. The scheduler (every run until the history is complete) does the rest. Per account it resolves the PUUID when unknown, confirms the server, refreshes rank and champion mastery, and collects the whole current season for every supported queue (Ranked Solo/Duo 420, Ranked Flex 440, Normal Draft 400, Blind 430, Swiftplay 480, Quickplay 490, Clash 700): the newest page first, then older pages resumed from `history_backfill` until the season start (1 January, or the day the season's first patch was seen if that came earlier; games are assigned to seasons by patch, so no season date is assumed), bounded per run so the tick stays inside its time budget. A game another linked account has already stored is folded from its stored record (`match_details`, reduced in the database to what folding reads) instead of being fetched from Riot again (`accounts/fold-input`); the record is used only when it lists the account, so a record stored under an earlier Riot key, or one of a game Riot no longer serves, sends the sync back to Riot. The production audit of 3 Nov 2026 counted 4,951 stored account games for 3,670 distinct games: about one match request in four had been for a game another account had already fetched. `account-sync`'s summary reports `fromRecords`. A game's role is Riot's team position, or its individual position when the team position is empty (as the stored record has always kept it), whichever account fetched it first. Each match is folded exactly once into `account_champion_history` (games/wins/KDA per champion, role, queue group and patch) through the `account_matches` ledger, so re-running or overlapping windows never double count. Nothing listed is skipped for good: when a run stops partway down a queue's newest page (its per-run limit, the time budget or a failed request) with games below the ones it stored still to fetch, the queue is marked for a rescan (`history_backfill` queue `rescan`), and once a later run completes that page, the older pages are read again from there, because new games arriving meanwhile could push the rest past the newest page, into the part of the list already read (a long gap between syncs; one list request per hundred stored games, which cost nothing else). Until then the queue keeps its state: a finished queue stays finished, so a game that fails every time holds nothing back beyond what it did before. A listed game for which Riot gives the same answer every time (404, or a reply that is not a readable match) is stored as a ledger row without a champion, like a remake (`game_creation` 0: Riot gave no time), so its queue still finishes. That happens only when a newer game of the same list reads in that run (if none was fetched, a stored one is read again first: the nearest folded game above it, or the queue's newest folded game), so a change in Riot's format or a fault in UNIIVERSE's own reading that breaks every game records nothing; the newest game of a queue, which Riot may still be preparing, is asked for again until a newer one has been read. The limit: a fault that breaks only some games (older ones, say) while newer games still read records those games as unavailable, and once one game on a page is recorded the rest of that page's refused games are recorded without another check. To collect them again after such a fault is fixed, delete the rows with `champion_id IS NULL AND game_creation = 0` and reset `history_backfill` for the accounts concerned (a one-off repair to propose with a rollback, not something the sync does). Riot's servers failing, the network and the rate limit are never recorded: a later run tries again. A game on a champion the champions table does not have yet (a new champion, before `version-check` has the Data Dragon version with it) is not stored, so a later run folds it once the champion is there; after three days it is stored without a champion like a remake, so a champion that never appears costs at most three days of one request per run. Several accounts of one player are combined by the proficiency service; a Riot ID that resolves to a PUUID already linked (a renamed account) is flagged as a duplicate and never counted twice. Demo accounts (label `demo`) are never synced. Once the current season is complete, spare budget collects the previous season the same way (`history_backfill.previous`), so last season can be shown with real numbers; older seasons are not collected. Sync states shown to players: Updating (being verified, or first games on the way) · Catching up on history (recent data in, older games of the season being added automatically) · Up to date · Delayed (no refresh for 6 h, or Riot unavailable; retried automatically) · Needs attention (Riot ID not found, duplicate), each with a sentence and "Last updated". "Retry sync" appears only for Delayed and Needs attention. Unlinking an account deletes its rows. A run in which any account it tried could not be synced for a reason Riot or the network caused is recorded as *degraded*, with the count in its error (never a Riot ID), so Admin → Data & Integrations shows it. An account that needs a person (a duplicate, an erased person, a Riot ID Riot does not know) is shown on its player's Riot Accounts tab and does not make every run degraded.

Raw facts (`riot_accounts`, `account_champion_history`, `account_mastery`) stay separate from the derived proficiency (`src/domain/proficiency`): games, recent games, games this patch, role usage, last played, mastery and results become a 0–1 score, a confidence and a tier (Main · Comfortable · Familiar · Few games · Out of practice · Not played; revision 2, see `docs/CHAMPION_EXPERIENCE_LABELS.md`). Proficiency never changes the pools; it rates the champions in them on Team Overview and the profile. Each player's profile shows the per-champion table with provenance (accounts, games analysed, current-patch games, last sync); the Owner sees raw sync diagnostics.

`account_matches` also keeps per-match facts (queue, champion, role, result, enemy champion in the same position, patch, duration), which Match History, Played Together and possible groups read without another Riot call.

### What the catch-ups do with a game they cannot read (4 Nov 2026)

The figures backfill, the timeline backfill and the sync's catch-up of older games (steps 2b and 2c: the figures and the full records of games stored before those were kept) read stored games newest first, and used to stop at the first error: a game Riot answers 5xx for (some corrupted games do, for good), 400, or with a body of an unexpected shape, at the head of any of them stopped it for the whole team on every run. `recordFailure` (`src/server/riot/api/client.ts`) decides what a failed request for one stored game's record means there: a refused key, a full rate limit or an unreachable Riot still stop the run at once (every further request would fail the same way); a 404 still marks the record unavailable, never to be asked for again; anything else is passed over: the run goes on to the next record, asks for the skipped one again on a later run, and marks it as nothing it is not. `MAX_SKIPPED_RECORDS` (3) bounds the requests a run spends on such records, so an outage stops a run as before. The two backfill jobs name the skipped ids in their log line and in the run's summary (`skipped`); the sync names them in the account's log line (`could not read …`), kept among the run's last log lines. A game on a queue's season list follows the sync's own rule above instead: only an answer that is the same every time (404, or an unreadable format) records it, and only once a newer game reads; Riot's servers failing hold the queue at that page until a later run.

A game whose record Riot no longer serves (a 404 in the catch-up) is marked on the ledger row (`kills = -1`, never read as a figure) and stored as an unavailable record (no players) at the same time, so every page says the record is gone rather than still being collected, and no backfill waits for it.

**A game a teammate stored that the account's own list never did** (data-audit's `placesMissingFromOwnHistory`: 96 places in 63 games for 2 members on 6 Nov 2026, every one a game of the season with no row at all for the member, in collected queues, with the member's season marked complete; most likely queues marked done by the paging before the rescan existed, since a done queue is never re-read) is folded from the stored record by the daily `integrity` job (`foldMissingPresences` in `accounts/sync.ts`): the records naming the account's PUUID on a side with no ledger row for it, newest first, at most 200 a day, through the same fold the sync uses for a listed game another account already stored (`foldGame` with the record: the same row, champion history and summary; a remake or an unknown champion treated as the sync would). No Riot request; on conflict nothing. A game only the account itself played (no teammate's record) cannot be recovered this way: that needs the account's list read again from the top.

**Held since 6 Nov 2026** (`FOLD_MISSING_PRESENCES` in `jobs/integrity.ts`). The first run (Data jobs 42181539020, on d087230) folded 200, its cap, where data-audit had counted 96. data-audit then read 0 places missing. The fold takes every stored record that names an account and has no row for it: games of earlier seasons and the accounts of personal-use profiles included, which data-audit never counts. A folded row cannot be told apart from a collected one afterwards (`account_matches` has no time of writing). So the daily job now only counts the candidates, by kind (`summary.missingPresences.kinds`: this season or earlier, team member or personal use), until the owner decides.

**Queues finished before the rescan existed** (`history-rescan`, a one-off job run by hand from Data jobs). A queue finished before #201 could have stopped with listed games still unread below its offset, and a finished queue is never read past its offset again. On 6 Nov 2026 rank-audit found four Solo/Duo lists one to six games short of Riot's own count, each with its season marked complete and no row without a champion. The job marks every finished queue of this season, on every player's account, for one rescan (`rescan: true`; `markHistoryRescan` in `jobs/history-rescan.ts`). The account's next sync then reads the older pages again through the sync's own rescan: one list request per hundred games, nothing for a game already stored, and a missing game folded as any listed game is. It adds rows only. Each account is marked under its sync lease, so no running sync writes its older state back. A busy account is left for the next run, so running it twice changes nothing. Every changed account's earlier `history_backfill` is kept first in `app_settings` (`history_rescan:previous`), so the marking can be undone. `tests/db/accounts.test.ts` ("history-rescan …") proves it end to end on a game removed from a finished 120-game queue.

**The account's sync lease** (`account_sync:<id>` in `app_settings`, `claimAccountSync`) is claimed by every sync of the account, not only the scheduler's and the visit refresh's: a profile's Refresh, the first sync after linking or replacing a Riot ID, and the owner's retry. Two syncs of one account never run at once (they would list and fetch the same games twice and write the history state last-writer-wins). A Refresh claims each account's lease right before reading it, never for the accounts its 40-second budget does not reach, and names an account it could not read beside its result instead of saying "no new games" for a check that did not happen. An account a person has to correct (a Riot ID Riot could not find, or the same Riot account as another linked one) counts as a failed attempt, so the scheduler's back-off applies and no page view retries it.

## Rank readings and LP per game (`rank-watch`)

A linked account's rank is read from LEAGUE-V4 (one request answers Solo/Duo and Flex) by account sync and by the rank watch. `rank_snapshots` keeps one row per change; an unchanged reading moves the last row's `confirmed_at` on (migration 0065), under a per-account-and-queue lock, so overlapping runs never duplicate a reading and a slow answer never moves one back. The rank watch (`src/server/jobs/rank-watch.ts`, in every tick, interval 5 minutes, and callable on its own at `/api/jobs/rank-watch`) reads the accounts that played ranked in the last 30 days every run and the others about hourly; at most 40 accounts a run, half of each rate-limit window, no retries, and a full limit or a refused key ends the run. A game's LP is never stored: it is worked out when a page shows it, from the readings around it (`src/domain/lp-attribution.ts`; the rule and its limits in [RANKED_PROGRESS.md](RANKED_PROGRESS.md)). `rank-audit` reports what the readings prove on real data, read-only.

## Ranks of a match's players

LEAGUE-V4 (`/lol/league/v4/entries/by-puuid/{puuid}`, the match's server) is asked about the other players of the members' games, and each answer is kept in `last_known_ranks` (both ranked queues, `UNRANKED` for a queue with no entry, `source` "match lookup"), at two moments:
- **After a game is collected** (the `rank-checks` job, in every scheduler tick after `account-sync`, due every 15 minutes, at most 15 s): the players of the members' games of the last 7 days with no check since that game ended, newest game first, 30 a run, so every recent card and scoreboard has the ranks around its game whether or not anyone opens it. It uses at most 600 of the day's checks and half of each rate-limit window: when its half of Riot's one-second window is full (about ten requests), it waits for the window to turn over, within its 15 s, and it leaves the rest to the next run when a wait gets nobody through (a longer window is full). A run in which every player it asked failed is *degraded* with a count-only message, which Admin repeats, and its log counts the failures by what they met (docs/MONITORING.md).
- **When a member opens a match**: its players with no check in the last 3 days, or none since a game of the last 7 days ended.

Members are never checked this way: their own sync reads their rank, and their rank history (`rank_snapshots`) gives their rank going into each game. At most 1,000 checks in any 24 hours across the site, half of each rate-limit window of that server (account sync keeps the other half), never a queued request, no retries. `data-audit` → `participantRanks` reports the coverage and the checks per day. Details: `src/server/players/participant-ranks.ts`, `docs/RIOT_COMPLIANCE.md` → Ranks in completed matches.

**Erased people** (`docs/PRIVACY.md`). The sync keeps the people whose personal data was erased out of everything it stores, through the erasure records (`erasureFilter`, `src/server/privacy/ledger.ts`):
- An erased person's own accounts are refused, before and after the PUUID is resolved, and logged only as `account 1a2b3c4d`.
- In anyone else's games they become a "Removed player": in `match_details`, in the figures and timeline backfills, and as a lane opponent (`enemy_champion_id`).
- They are matched by PUUID, or by Riot ID when a new API key changed the PUUIDs; a PUUID learned that way is added to their record.
- Sync log lines name accounts by a short id, never a Riot ID.

## Health and self-monitoring

`data_refresh_status` records each job's last start/success/failure, error, duration and consecutive failures. Admin → Data & Riot and `/api/health` surface warnings when a pipeline is stale (the version check silent for 26 hours) or failing repeatedly. A run killed before it finished (a function timeout, a crash) counts as a failed run: the next run of the job, starting once it has said "running" for 15 minutes, records it (one more consecutive failure, `last_failure_at`, "Run never finished (process was interrupted).") and closes its `job_runs` row as failed; until then a run past those 15 minutes already counts as failed in the warnings and `/api/health`. The `integrity` job (daily) unsticks job states left running by an interrupted process the same way (counted as a failed run) and closes every `job_runs` row left open for over 30 minutes, deletes sign-in sessions a week after they ended, failed sign-ins older than the throttling window and run records older than 60 days, in bounded batches. It also re-applies the personal-data erasure records to anything stored in the last two days, as a safety net, and reports a degraded run when a record was made under another `UNIIVERSE_AUTH_SECRET`. `erasure-reconcile` (on demand only) re-applies them to the whole database, after a restore (`docs/BACKUPS.md`).

## Retired tables (Meta & Trends, removed 2026-10-19)

Meta & Trends (Solo Queue Meta, Duo Synergies, Pro Play) collected high-Elo ranked games from every public server and professional games from Leaguepedia, and aggregated them into pick, ban, matchup, synergy and draft-slot statistics. The feature and its jobs (`ranked-discover`, `ranked-ingest`, `aggregate`, `pro-sync`) were removed; nothing writes these tables any more:

| Tables | Held | Still read by |
|---|---|---|
| `ranked_matches`, `ranked_participants`, `ranked_bans`, `match_fetch_queue`, `region_status` | Collected high-Elo games and the collection queue | nothing |
| `stat_periods`, `stat_region_periods`, `stat_rank_periods`, `champion_role_stats`, `champion_ban_stats`, `champion_matchups`, `champion_synergies`, `pro_pick_slot_stats` | Aggregated statistics | nothing |
| `pro_games`, `pro_game_picks`, `pro_game_bans` | Professional games | nothing |
| `champion_change_points` | Detected champion reworks (discounted old statistics) | nothing |
| `tracked_summoners` | High-Elo ladder players | nothing: migration `0048` copied the ranks Match History shows for other players into `last_known_ranks` |

**Migration `0062_retire_meta_trends_tables`** dropped 12 of them on 4 Nov 2026 (#86, audit decision 2): `ranked_matches`, `ranked_participants`, `ranked_bans`, `match_fetch_queue`, `champion_role_stats`, `champion_ban_stats`, `champion_matchups`, `champion_synergies`, `pro_pick_slot_stats`, `pro_games`, `pro_game_picks` and `pro_game_bans`, about 206 MB. It merged after a verified backup that holds them (`docs/BACKUPS.md`; the 2 Nov copy, kept until 30 Nov 2026, is the last weekly copy with them) and production checks that nothing read them (Data jobs `db-usage`). Recovery: `pg_restore --table` from that backup, then revert the change.

The rest (`region_status`, `champion_change_points`, the `stat_*_periods` tables and `tracked_summoners`) stay defined in `src/server/db/schema` so `drizzle-kit generate` never emits a `DROP`. Dropping them deletes the collected global data for good, so it is a separate migration that needs the owner's approval; it never touches user, team, champion or match records (`account_*`, `match_details`, `champions` and the rest stay). Match History's last-known ranks no longer depend on any of them (`last_known_ranks`, migration `0048`). Old status rows of the retired jobs stay in `data_refresh_status` and `job_runs` and are hidden (`RETIRED_JOB_KEYS` in `src/server/ops/refresh-status.ts`).

**Checking a drop against production first.** Data jobs `db-usage` reports `retired`: for these tables (the ones still kept included, with the period tables' `stat_source` enum type) and the removed Draft feature's (`docs/ARCHITECTURE.md`, "Draft removed"), each one's rows, reads (sequential and index scans) and writes since the statistics were last reset (`statsReset`); the Draft's two columns and six enum types; Riot accounts of the legacy opponent type; and anything outside them that depends on them (foreign keys, views, columns of a retired type, publications). It also counts other players' last known ranks by source (`lastKnownRanks`), and how many of them no stored game names: only a player in a stored game is ever shown, so those are what a prune of `last_known_ranks` would delete. Counts only, never a PUUID. A drop merges only after a verified backup and when two runs a day apart show no new reads or writes and no dependent other than the `riot_accounts` foreign key that goes with its own column. Afterwards the same report shows each of them as gone.

# Data pipelines

UNIIVERSE collects two kinds of data: Riot's static game data (champions, skins, patches) and the linked players' own Riot accounts (games, ranks, mastery). Every pipeline follows the same shape: **external provider → adapter → validation → normalised tables**. Provider quirks never reach the pages.

## Riot static data (Data Dragon)

`version-check` (hourly) fetches `versions.json`. When the newest version differs from the stored current patch it downloads `champion.json` and the per-champion files, upserts champions (new ones get `firstSeenVersion`) and their skins, opens the new patch as *current* and clears caches; item, summoner spell and rune names for the match history follow once per game version. If Data Dragon is unreachable and the database is empty, an offline fixture seeds the roster so development can continue; it is replaced by the first successful sync.

## Riot requests

Riot rate-limits each host separately, and the client keeps one sliding-window limiter per host (`RateLimiterPool`, `RIOT_RATE_LIMITS`, default dev/personal-key limits 20/1 s and 100/120 s per host), honours `Retry-After` on 429, backs off exponentially on 5xx and retries a bounded number of times. Jobs stop at their time budget and resume on the next run. Servers are resolved through the single platform registry in `src/domain/riot-platforms.ts` (17 public League servers, no Chinese servers); `RIOT_PLATFORMS` only names the server the key check asks.

## Linked Riot accounts (`account-sync`)

Players link Riot accounts by Riot ID (`GameName#TAG`, stored exactly as typed). ACCOUNT-V1 requests go to the americas, asia or europe routing value (`accountRegionFor` in `src/domain/riot-platforms.ts`): Riot does not serve that API from the `sea` host that carries OCE and South-East Asian match data, and asking it there answers 403, which is indistinguishable from a rejected key. Resolution is real and in this order: ACCOUNT-V1 `by-riot-id` → PUUID (the canonical identity; Riot's own spelling of the name is adopted), then ACCOUNT-V1 `region/by-game/lol/by-puuid` → the server the account actively plays on, which replaces the sign-up region selection (`platform_source = riot`); if that lookup is unavailable the selected server stays (`platform_source = user`, OCE by default). Sign-up never waits for Riot: accounts are inserted as `never`, a best-effort verification runs right after the sign-up response (`kickoffAccountSync`), and anything Riot could not answer is stored as `pending` with a plain-language reason and retried by the job.

Every tick (`account-sync` is due every 15 minutes) works through the linked accounts most urgent first: new or failing links (retried with back-off: 5 minutes after the first failure, doubling per attempt up to 6 hours), accounts still collecting this season's history (every run until complete), accounts of active players (main group, or signed in during the last week) not refreshed for 45 minutes (`ACCOUNT_SYNC_ACTIVE_AGE_MINUTES`), then everyone else after 3 hours (`ACCOUNT_SYNC_MIN_AGE_MINUTES`); only player accounts are refreshed; `ACCOUNT_SYNC_BATCH` and `ACCOUNT_SYNC_PENDING_BATCH` bound a run so failing links never starve the rest. Opening a player's overview, profile or Riot settings also refreshes that player's due accounts in the background (about 40 seconds, 60 matches, a two-minute lease per player), and the open page checks a short version of its data (every 10 seconds while that refresh runs, every 30 while older games are still being added, less and less often otherwise, never while the tab is hidden) and reads itself again only when it changed (`docs/ARCHITECTURE.md`, "Pages that update themselves"), so history fills in while it is watched. Per account it resolves the PUUID when unknown, confirms the server, refreshes rank and champion mastery, and collects the whole current season for every supported queue (Ranked Solo/Duo 420, Ranked Flex 440, Normal Draft 400, Blind 430, Swiftplay 480, Quickplay 490, Clash 700): the newest page first, then older pages resumed from `history_backfill` until the season start (1 January, or the day the season's first patch was seen if that came earlier; games are assigned to seasons by patch, so no season date is assumed), bounded per run so the tick stays inside its time budget. Each match is folded exactly once into `account_champion_history` (games/wins/KDA per champion, role, queue group and patch) through the `account_matches` ledger, so re-running or overlapping windows never double count. Nothing listed is skipped for good: when a run stops partway down a queue's newest page (its per-run limit, the time budget or a failed request) with games below the ones it stored still to fetch, the queue is read again from the top once that page is complete, because new games arriving meanwhile could push the rest past the newest page, into the part of the list already read (a long gap between syncs; one list request per hundred stored games, which cost nothing else). A listed game for which Riot gives the same answer every time (404, or a reply that is not a readable match) is stored as a ledger row without a champion, like a remake (`game_creation` 0: Riot gave no time), so its queue still finishes. That happens only when a newer game of the same list reads in that run (if none was fetched, a stored one is read again first), so a change in Riot's format or a fault in UNIIVERSE's own reading records nothing; the newest game of a queue, which Riot may still be preparing, is asked for again until a newer one has been read. Riot's servers failing, the network and the rate limit are never recorded: a later run tries again. A game on a champion the champions table does not have yet (a new champion, before `version-check` has the Data Dragon version with it) is not stored, so a later run folds it once the champion is there; after three days it is stored without a champion like a remake, so a champion that never appears costs at most three days of one request per run. Several accounts of one player are combined by the proficiency service; a Riot ID that resolves to a PUUID already linked (a renamed account) is flagged as a duplicate and never counted twice. Demo accounts (label `demo`) are never synced. Once the current season is complete, spare budget collects the previous season the same way (`history_backfill.previous`), so last season can be shown with real numbers; older seasons are not collected. Sync states shown to players: Updating (being verified, or first games on the way) · Catching up on history (recent data in, older games of the season being added automatically) · Up to date · Delayed (no refresh for 6 h, or Riot unavailable; retried automatically) · Needs attention (Riot ID not found, duplicate), each with a sentence and "Last updated". "Retry sync" appears only for Delayed and Needs attention. Unlinking an account deletes its rows.

Raw facts (`riot_accounts`, `account_champion_history`, `account_mastery`) stay separate from the derived proficiency (`src/domain/proficiency`): games, recent games, games this patch, role usage, last played, mastery and results become a 0–1 score, a confidence and a tier (Main · Comfortable · Familiar · Few games · Out of practice · Not played; revision 2, see `docs/CHAMPION_EXPERIENCE_LABELS.md`). Proficiency never changes the pools; it rates the champions in them on Team Overview and the profile. Each player's profile shows the per-champion table with provenance (accounts, games analysed, current-patch games, last sync); the Owner sees raw sync diagnostics.

`account_matches` also keeps per-match facts (queue, champion, role, result, enemy champion in the same position, patch, duration), which Match History, Played Together and possible groups read without another Riot call.

## Ranks of a match's players

LEAGUE-V4 (`/lol/league/v4/entries/by-puuid/{puuid}`, the match's server) is asked about the other players of the members' games, and each answer is kept in `last_known_ranks` (both ranked queues, `UNRANKED` for a queue with no entry, `source` "match lookup"), at two moments:
- **After a game is collected** (the `rank-checks` job, in every scheduler tick after `account-sync`, due every 15 minutes, at most 15 s): the players of the members' games of the last 7 days with no check since that game ended, newest game first, 30 a run, so every recent card and scoreboard has the ranks around its game whether or not anyone opens it. It uses at most 600 of the day's checks and half of each rate-limit window: when its half of Riot's one-second window is full (about ten requests), it waits for the window to turn over, within its 15 s, and it leaves the rest to the next run when a wait gets nobody through (a longer window is full).
- **When a member opens a match**: its players with no check in the last 3 days, or none since a game of the last 7 days ended.

Members are never checked this way: their own sync reads their rank, and their rank history (`rank_snapshots`) gives their rank going into each game. At most 1,000 checks in any 24 hours across the site, half of each rate-limit window of that server (account sync keeps the other half), never a queued request, no retries. `data-audit` → `participantRanks` reports the coverage and the checks per day. Details: `src/server/players/participant-ranks.ts`, `docs/RIOT_COMPLIANCE.md` → Ranks in completed matches.

**Erased people** (`docs/PRIVACY.md`). The sync keeps the people whose personal data was erased out of everything it stores, through the erasure records (`erasureFilter`, `src/server/privacy/ledger.ts`):
- An erased person's own accounts are refused, before and after the PUUID is resolved, and logged only as `account 1a2b3c4d`.
- In anyone else's games they become a "Removed player": in `match_details`, in the figures and timeline backfills, and as a lane opponent (`enemy_champion_id`).
- They are matched by PUUID, or by Riot ID when a new API key changed the PUUIDs; a PUUID learned that way is added to their record.
- Sync log lines name accounts by a short id, never a Riot ID.

## Health and self-monitoring

`data_refresh_status` records each job's last start/success/failure, error, duration and consecutive failures. Admin → Data & Riot and `/api/health` surface warnings when a pipeline is stale (the version check silent for 26 hours) or failing repeatedly. The `integrity` job (daily) unsticks job states left running by an interrupted process, deletes sign-in sessions a week after they ended and prunes failed sign-ins older than the throttling window, in bounded batches. It also re-applies the personal-data erasure records to anything stored in the last two days, as a safety net, and reports a degraded run when a record was made under another `UNIIVERSE_AUTH_SECRET`. `erasure-reconcile` (on demand only) re-applies them to the whole database, after a restore (`docs/BACKUPS.md`).

## Retired tables (Meta & Trends, removed 2026-10-19)

Meta & Trends (Solo Queue Meta, Duo Synergies, Pro Play) collected high-Elo ranked games from every public server and professional games from Leaguepedia, and aggregated them into pick, ban, matchup, synergy and draft-slot statistics. The feature and its jobs (`ranked-discover`, `ranked-ingest`, `aggregate`, `pro-sync`) were removed; nothing writes these tables any more:

| Tables | Held | Still read by |
|---|---|---|
| `ranked_matches`, `ranked_participants`, `ranked_bans`, `match_fetch_queue`, `region_status` | Collected high-Elo games and the collection queue | nothing |
| `stat_periods`, `stat_region_periods`, `stat_rank_periods`, `champion_role_stats`, `champion_ban_stats`, `champion_matchups`, `champion_synergies`, `pro_pick_slot_stats` | Aggregated statistics | nothing |
| `pro_games`, `pro_game_picks`, `pro_game_bans` | Professional games | nothing |
| `champion_change_points` | Detected champion reworks (discounted old statistics) | nothing |
| `tracked_summoners` | High-Elo ladder players | nothing: migration `0048` copied the ranks Match History shows for other players into `last_known_ranks` |

**Migration `0062_retire_meta_trends_tables`** drops 12 of them (audit decision 2): `ranked_matches`, `ranked_participants`, `ranked_bans`, `match_fetch_queue`, `champion_role_stats`, `champion_ban_stats`, `champion_matchups`, `champion_synergies`, `pro_pick_slot_stats`, `pro_games`, `pro_game_picks` and `pro_game_bans`, about 206 MB. It merges only after a verified backup that holds them (`docs/BACKUPS.md`) and a day with no reads of them (Data jobs `db-usage`). Recovery: `pg_restore --table` from that backup, then revert the change.

The rest (`region_status`, `champion_change_points`, the `stat_*_periods` tables and `tracked_summoners`) stay defined in `src/server/db/schema` so `drizzle-kit generate` never emits a `DROP`. Dropping them deletes the collected global data for good, so it is a separate migration that needs the owner's approval; it never touches user, team, champion or match records (`account_*`, `match_details`, `champions` and the rest stay). Match History's last-known ranks no longer depend on any of them (`last_known_ranks`, migration `0048`). Old status rows of the retired jobs stay in `data_refresh_status` and `job_runs` and are hidden (`RETIRED_JOB_KEYS` in `src/server/ops/refresh-status.ts`).

**Checking a drop against production first.** Data jobs `db-usage` reports `retired`: for these tables and the removed Draft feature's (`docs/ARCHITECTURE.md`, "Draft removed"), each one's rows, reads (sequential and index scans) and writes since the statistics were last reset (`statsReset`); the Draft's two columns and six enum types; Riot accounts of the legacy opponent type; and anything outside them that depends on them (foreign keys, views, columns of a retired type, publications). A drop merges only after a verified backup and when two runs a day apart show no new reads or writes and no dependent other than the `riot_accounts` foreign key that goes with its own column. Afterwards the same report shows each of them as gone.

## Dropped tables (Clash Scout, retired 2026-10-23)

Clash Scout was removed (`docs/CLASH_SCOUT.md`). Its pages, actions, Riot requests and its on-demand `lab-benchmark` job went first; migration `0064` then dropped its two tables, after the owner had verified a recent backup:

| Tables | Held |
|---|---|
| `clash_scouts` | The scouts the team saved: the opponents' names, ranks, champion figures and mastery read from Clash's screenshots, and the Riot ID and PUUID of each opponent a member verified |
| `clash_scout_accounts` | The verified PUUIDs of each saved scout |

The same change removed their schema (`src/server/db/schema/clash.ts`) and the code that cleared erased people from them (permanent erasure and its reconciliation). `db-usage` keeps listing them among `retired`, reported as gone. Old `lab-benchmark` status rows are hidden like the other retired jobs' (`RETIRED_JOB_KEYS`). Recovery, if ever needed: `pg_restore --table` from that backup, then revert the change.
